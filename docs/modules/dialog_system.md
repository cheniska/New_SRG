# Dialog System

Модули: `Assets/Scripts/Dialog/*.cs`. Конфиги: `Assets/Config/DialogsConfig.json`
(структура) + секция `"Dialog"` в `Assets/Config/TextsConfig.json` (все фразы).

Ядро — `DialogService` (реестры, навигация, подстановка, условия). Прикладные ветки лежат в
`Dialog*Actions`; их список и установка — в `DialogModules`. Общие мелочи: `DialogContextExt`
(чтение/запись `ctx.Data`), `DialogBargain` (механика торга суммой).

## 1. Назначение

Диалоги с кораблями, планетами и станциями: дерево узлов, реплики с условиями видимости,
действия при выборе реплики, вариативные фразы из пулов, приветствия по правилам матчинга.

**Главное правило: структура и текст лежат в разных файлах.**

| Файл | Что содержит | Чего в нём быть не должно |
|---|---|---|
| `DialogsConfig.json` | деревья, `StartNode`/`NextNode`, `Condition`, `Actions`, правила приветствий (условия матчинга), `Tuning` (только числа) | фраз: ни инлайновых фоллбэков `{tag\|фраза}`, ни `StringPools`, ни `Texts` в правилах приветствий, ни подписей/меток в `Tuning` и `DialogUI` |
| `TextsConfig.json` → `"Dialog"` | `TagDefaults`, `Speakers`, `PoolDefaults`, `Pools`, `Greetings`, `Phrases`, `GreetingDefaults` | структуры и условий |
| C#-код | логику | **строковых литералов с фразами** — всё, что видит игрок, идёт через `DialogTexts` |

Правило распространяется и на код: подпись кнопки, пометка в списке выбора, заголовок-заглушка,
формат склейки «тип «имя»» — это фразы, и они читаются из `Phrases`/`GreetingDefaults`, а не
пишутся литералами. Отсутствующий ключ даёт **пустую строку и warning в лог** — намеренно:
литерал-«подстраховка» на русском пережил бы любую локализацию и молча уехал бы игроку.

Связывает их `DialogTexts.Link(dialogs, texts)` на загрузке (`GalaxyManager.EnsureContextInitialized`,
до валидации): `Pools` заливаются в `DialogsConfig.StringPools`, `Greetings` — в `GreetingRule.Texts`
по `Id` правила. Поэтому рантайм (`PickFromPool`, селекторы приветствий) читает те же поля, что и
раньше, и про разделение файлов не знает.

## 2. Подстановка тегов

`DialogService.Substitute(text, ctx)` заменяет `{tag}` в `Text`, `Speaker`, `Title` и текстах реплик.
Порядок для каждого тега:

1. **Резолвер** — `RegisterTag` / `RegisterParamTag` (см. `DialogActions.RegisterDefaultTags`).
   Непустой результат выигрывает всегда.
2. **Дефолт из текст-конфига** — `DialogTexts.ResolveDefault`:
   - `{speaker_name}` → `Speakers[dialogId]` (учитывает `AliasOf`);
   - точный ключ в `TagDefaults`;
   - для `{pool:X}` → `PoolDefaults[X]` (полный шаблон, напр. `Attack.<ShipType>Ok`),
     затем `PoolDefaults` по семейству (часть до первой точки);
   - маска в `TagDefaults` со `*` — один ключ `nav_star_*_dist` покрывает все восемь слотов.
3. **Видимый `{tag}`** — если дефолта нет. Это намеренно: дырка должна быть заметна.

Пустая строка в `TagDefaults` — **валидный** дефолт («подставить ничего»), это не то же самое, что
отсутствие ключа. Отличать по `null`, а не по `IsNullOrEmpty`.

Результат подстановки прогоняется рекурсивно (до `MaxSubstituteDepth = 4`), поэтому дефолт может
сам содержать теги: `"Получил свои {extort_fee} кр."`. Тег, оставшийся как `{tag}`, не рекурсируется.

### `{ship_name}` против `{speaker_name}`

Два разных смысла, которые раньше сидели на одном теге и разъезжались инлайновыми фоллбэками:

- `{speaker_name}` — **кто говорит**; в поле `Speaker`. Дефолт — должность из `Speakers[dialogId]`
  («Дежурный медик» для `Station_MC_gov`).
- `{ship_name}` — **собственное имя** корабля/станции внутри фразы («станция «{ship_name}»»).
  Дефолт пустой.

Оба резолвятся из `TargetShip.Name`; расходятся только дефолтами.

## 3. Условия видимости реплик — гибрид

`Condition` у реплики вычисляется на **каждый рендер узла** (`GetVisibleReplies`), поэтому цена
важна: у `Ship_default/intro` 15 реплик, и половина условий опирается на теги, за которыми стоят
сервисные `Preview` (см. §3.1 про кэш).

**Тег-DSL (по умолчанию)** — для простых проверок, ~130 из 136 условий в конфиге:

```
"Condition": "can_trade == \"1\" && player_is_pirate == \"0\""
```

Поддержка: `&& || !`, скобки, `== != > < >= <=`. Атом — `тег op значение` либо одиночный тег как
boolean (пусто/`0`/`false`/`no`/`нет` → false). Сравнение числовое, если обе стороны парсятся во
float, иначе регистронезависимое строковое. Реализация — `DialogService.DefaultEvaluateCondition`.

**Lua (префикс `lua:`)** — когда нужны настоящая логика, обход коллекций, арифметика:

```
"Condition": "lua: target ~= nil and target.Race:find('Dominator') == nil"
"Condition": "lua: is('can_trade') and not is('player_is_pirate')"
"Condition": "lua: tonumber(tag('reward_amount')) > 500"
```

Окружение готовит `DialogService.BuildLuaEnv`: `ctx`, `player`, `target`, `planet` плюс мост в
тег-словарь — `tag(name)` (строка, никогда не nil) и `is(name)` (boolean по правилам DSL). Мост
существует, чтобы Lua-условие говорило на том же языке, что и DSL, и одно можно было переписать в
другое без изменения тегов.

`Actions` умеют то же через поле `Script` вместо `Method` (тогда `Method` игнорируется); там
дополнительно доступен `args`.

**Выбор:** DSL — для `тег == значение`; Lua — когда DSL пришлось бы выкручивать. Переводить
существующие условия на Lua ради единообразия не нужно.

### Кэш чанков

`LuaHost.EvalCached(source, locals)` компилирует чанк один раз и переиспользует; окружение живёт
вместе с чанком, локалы перезасеваются перед вызовом (ключи прошлого вызова, отсутствующие в новом,
гасятся в `nil` — иначе всплывёт `target` от предыдущего диалога). Кэш ключуется исходником, поэтому
годится **только для строк из конфига**. Для строк, склеенных из рантайм-значений, — `DoWithEnv`,
иначе кэш растёт без предела.

`LuaHost.Precompile(source)` — компиляция без исполнения; ей пользуется валидатор.

### 3.1 Memo-кэш резолва тегов

Один рендер узла резолвит теги многократно: условия всех реплик, `TextVariants`, текст узла и
подпись каждой кнопки. В `Ship_default/intro` теги `is_hireable`, `player_is_pirate` и
`is_partner_of_player` стоят каждый в двух условиях, а `can_trade`/`can_extort`/`can_rob_cargo`/
`needs_truce`/`can_protect`/`can_preserve` — это по сервисному `Preview` на каждый.

`DialogService.ResolveTag` мемоизирует результат до ближайшей мутации состояния.
`InvalidateTagCache()` вызывается на смене узла/контекста (`Start`/`Push`/`End`/`Pop`/`EnterNode`)
и **вокруг каждого действия** — до и после: действие и пишет `ctx.Data`, и само читает теги
(Lua-скрипты зовут `tag()`/`is()`). Внутри прохода рендера действий не выполняется, поэтому
значения стабильны. Кэш привязан к конкретному `DialogContext`: у поддиалога свой `Data`.

**Недетерминированные теги обязаны регистрироваться как volatile** —
`RegisterTag(name, resolver, isVolatile: true)`. Это всё, что тянет строку из пула: `pool`,
`plural`, `trade_intro`, `order_ack`, `dropcargo_ack`, `drone_land_target`. Иначе два `{pool:X}`
в одном узле вернут одну и ту же фразу вместо двух разных — ровно то, ради чего у пулов свой RNG.

## 4. Пулы вариативных фраз

`{pool:Key}` → случайная строка из `Pools[Key]` (`DialogService.PickFromPool`). В ключе
раскрываются `<ShipType>`, `<Race>`, `<DominatorClass>` (последний — через
`Tuning.DominatorClassMap`), см. `DialogActions`. Если пул отсутствует или пуст — работает
`PoolDefaults` (§2).

### Плейсхолдеры внутри строк пулов

Строки пулов (наследие SR2-текстов) используют **другой** синтаксис — `<Player>`, `<Money>`,
`<Target>`. `DialogService.PickFromPool` возвращает строку как есть; раскрывают их вызывающие:

- **диалоги** — `DialogActions.ExpandPoolPlaceholders` переводит `<X>` в обычный `{тег}`, а дальше
  работает рекурсия `Substitute`, так что вся логика остаётся в существующих резолверах;
- **`NpcConversationLog`** — подставляет свои пары значений при публикации переговоров в новости.

Таблица (порядок замен важен: `<ShipBad>` до `<Ship>`, иначе префикс съест его):

| плейсхолдер | тег | смысл |
|---|---|---|
| `<Player>`, `<Ranger>` | `{player_name}` | игрок |
| `<Ship>`, `<ShipName>`, `<FullShip>` | `{ship_name}` | цель диалога |
| `<HomePlanet>` | `{home_planet}` | родная планета цели |
| `<Partner>` | `{partner_leader_name}` | рейнджер, уже нанявший цель |
| `<Target>`, `<ShipBad>`, `<FullShipBad>` | `{third_party_name}` | третья сторона |
| `<Money>` | `{money_amount}` | сумма текущего торга |
| `<Month>` | `{partner_months}` | срок контракта |
| `<ObjectName>` | `{order_object_name}` | цель приказа о посадке/атаке |
| `<Star>` | `{order_star_name}` | цель приказа о гиперпрыжке |
| `<Item>` | `{item_name}` | предмет |
| `<Cnt>` | `{trade_buy_limit}` | сколько ед. NPC способен купить |
| `<List>`, `<Land>` | `{drone_allow_list}`, `{drone_land_target}` | разрешения подчинённого (§6) |
| `<Name>` | `{dom_program_name}` | имя программы доминатора |

`{money_amount}` и `{third_party_name}` — составные: одна и та же фраза пула переиспользуется в
ветках, где сумма/третья сторона лежат под разными ключами, поэтому теги пробуют ключи `ctx.Data`
по порядку и берут первый заполненный (`extort_demand` → `ransom_offer` → `partner_offer` → …).
Это безопасно, потому что `Push` создаёт новый контекст со своим `Data`, и одновременно заполнены
только ключи текущей ветки. Читают `Data` напрямую, а не через одноимённые теги: у тех непустые
дефолты (`"0"`), и «первый непустой» всегда цеплялся бы за первый кандидат.

В **ключе** пула раскрываются `<ShipType>`, `<Race>`/`<ShipRace>`, `<PlayerRace>`,
`<DominatorClass>`, `<Ship>`, `<Player>` — это позволяет одним тегом ссылаться на расовые и
типовые варианты (`{pool:Attack.<ShipType>Ok}`).

### Склонения

`{plural:N.Form}` — русское склонение по пулам `Count.<0|1|2><Form>` (`1Day`=«день», `2Day`=«дня»,
`0Day`=«дней»). Вместо числа можно указать имя тега: `{plural:cargo_rob_containers.Unit}` —
имя параметр-тега вычисляется до подстановки, поэтому вложенный `{tag}` там не работает.
Заменяет костыли вида «контейнер(ов)».

## 5. Кто говорит: реплики NPC против реплик игрока

Схемы SR2HD (`docs/design/Space_Dialog_Schemes.txt`, `Base_Dialog_Schemes.txt`) размечают это явно, и
разметку надо соблюдать — иначе игрок «говорит» словами NPC:

| в схеме | что это | куда в конфиге |
|---|---|---|
| `[X]` | пункт меню игрока | `Replies[].Text` |
| `(X)` | реплика NPC | `Node.Text` |

По именам пулов это тоже видно: `*.PlayerSend`, `PlayerOk`, `PlayerLess`, `PlayerMore`,
`PlayerDismiss*`, `OrderForAll`, `OrderForYou`, `FlyToMe`, `FlyToStar`, `LandingToObject` — игрок;
`Computer*`, `Answer*`, `Is*`, `Ok`, `Suspect`, `SmallMoney`, `Greeting`, `*Ask` — NPC.

Для узлов-исходов, где реплика NPC зависит от кода причины, есть **`TextVariants`** — список
`{Condition, Text}`, из которого берётся первый подошедший вариант (иначе `Text`):

```json
"result": {
  "TextVariants": [
    { "Condition": "extort_reason == \"Accepted\"",     "Text": "{pool:Money.<ShipType>Ok}" },
    { "Condition": "extort_reason == \"SumIsVeryBig\"", "Text": "{pool:Money.<ShipType>SumIsVeryBig}" }
  ],
  "Replies": [ { "Text": "{pool:To}", "Condition": "extort_reason == \"Accepted\"", "Actions": [ … ] } ]
}
```

Условия на репликах при этом остаются — у исходов различается ещё и навигация (часть возвращает
в узел торга). Раньше `TextVariants` не было, реплики NPC приходилось раскладывать по условным
`Reply`, и игрок нажимал кнопки со словами собеседника.

Плейсхолдеры-обращения относительны говорящему, поэтому подстановка знает, чью реплику рендерит
(`DialogService.Substitute(text, ctx, DialogVoice)`): `<Player>`/`<Ranger>` в реплике NPC — это
игрок, а в реплике игрока — собеседник. «Иди под мое командование, `<Ranger>`» обращено к NPC,
«Ты не похож на лидера, `<Ranger>`» — к игроку.

Кода, который сам выбирает реплику (`{order_ack}`, `{dropcargo_ack}`, `{trade_intro}`), это тоже
касается: он берёт строку через `DialogActions.PickPoolLine`, а не через `PickFromPool` — иначе
`<…>`-плейсхолдеры останутся сырыми.

### Обновление реплики NPC на месте

Реплика игрока меняет цифру в словах собеседника («в 2 раза меньше» при найме, «следующая цель»
при совместной атаке) простым `NextNode` на **тот же самый узел**: `EnterNode` заново шлёт
`OnDialogNodeChanged`, и UI перерисовывает и текст, и кнопки.

Реакция должна быть **немедленной**, а не по нажатию «согласен». Везде, где у узла есть
регулируемое состояние, реплика собеседника считается по нему живым вердиктом (тег зовёт
`Preview`-метод сервиса, ничего не совершая), а кнопка подтверждения гейтится тем же вердиктом:

| узел | что регулируется | тег вердикта |
|---|---|---|
| `SpaceTalk_Partner/offer`, `SpaceTalk_Pirate/offer` | сумма найма | `{partner_offer_verdict}` |
| `SpaceTalk_Money/offer` | требуемая сумма | `{extort_verdict}` |
| `SpaceTalk_Truce/offer` | предлагаемый выкуп | `{truce_verdict}` |
| `SpaceTalk_Attack/pick` | выбранная цель | `{jatk_verdict}` |

Торговое меню (`SpaceTalk_Trade/menu`) гейтится проще — тегами `has_cargo`/`player_has_cargo`:
кнопка сделки не показывается, если у стороны нечем торговать.

Пример для найма:

```
(готов за 2X) [меньше] → (готов за X) [меньше] → (слишком мало) [удвоить] → (готов за X) [договорились]
```

Кнопка «договорились» видна только при `Accepted`; торг («меньше»/«удвоить») — пока причина
в деньгах (`Accepted`/`OfferTooLow`). Жёсткие отказы (характер, свита полна, ранг, уже нанят)
называются своими репликами сразу в узле торга — тем же мапингом «причина → пул», что и в `result`.

**Кошелёк игрока в торге не участвует.** Цену называет пилот (`PartnerService.CalcFee` —
вынесена из `Preview` именно для этого, считается без оглядки на деньги нанимателя), игрок её
двигает, и «мало» звучит только когда игрок сам увёл сумму ниже запроса. Отсюда три правила:

- `PartnerOfferInit` засевает **`2 × fee`**, без потолка по деньгам. Запас нужен, иначе торговаться
  нечем: цель принимает только `offer >= fee`, и первое же «в 2 раза меньше» било бы в отказ.
  На итоговую цену это не влияет — `TryHire` списывает рассчитанный `fee`, а не предложение.
- `PartnerOfferMore` не ограничен кошельком: пообещать можно больше, чем есть.
- Тег вердикта переводит `NotEnoughMoney` в `Accepted`. Пилот в чужой счёт не смотрит и
  соглашается на устраивающую его сумму; нехватка всплывает при самом найме, в узле `result`.

Пока это не было разведено, торг «подсматривал» кошелёк: у бедного игрока «удвоить» упиралось
в потолок, сумма не могла дорасти до запроса, и «слишком мало» висело вечно.

Отсюда правило: **`OnEnter` самовозвратного узла обязан быть идемпотентным.** Иначе он затирает
только что сделанное изменение, и игрок видит прежнее число — ровно так ломались торг за найм,
вымогательство, перемирие (`*Init` перезаписывали сумму) и выбор цели (`JointAttackListTargets`
сбрасывал выбор на первую строку). Сейчас `*Init` засевают значение только при отсутствии ключа,
а список целей пересобирается всегда, но сохраняет выбор, если цель ещё жива.

### Фабрика торга (`DialogBargain`)

Наём, перемирие и вымогательство — одна механика: засеять сумму → `/2` → `×2` → закрыть сделку,
плюс тег живого вердикта. Она описана один раз в `DialogBargain`, ветки задают только `BargainSpec`
(имена действий из JSON, ключи в `Data`, `Seed`/`Verdict`/`Commit` и два флага). Идемпотентность
`Init`, нижняя граница в 1 кредит и «вердикт считается через `Preview`, а не через `Try*`» стали
структурными — раньше каждое из этих правил было отдельным исправленным багом в каждой из трёх копий.

Различия, которые обязаны остаться различиями:

| | наём | перемирие | вымогательство |
|---|---|---|---|
| `CapMoreByPlayerMoney` | нет — сумма это обещание | **да** — платит игрок | нет — платит цель |
| `NotEnoughMoney` в вердикте | → `Accepted` | → `Accepted` | остаётся отказом |
| `SeedNeedsPlayer` | да | да | **нет** — сумму называет вымогатель по возможностям жертвы |

### Установка модулей и `Reset`

Список веток — в `DialogModules._modules`, там же единственный флаг «уже поставлено». Новый модуль
добавляется одной строкой туда и больше нигде; `DialogUIController.Awake` зовёт `DialogModules.Install()`.

`DialogService.Reset()` чистит реестры и **переустанавливает модули** через хук `ModuleReinstaller`.
Пока флаги «уже зарегистрировано» жили в самих модулях, Reset был ловушкой отложенного действия:
реестры он очищал, а повторная регистрация выходила по первой строке — и все действия с тегами
исчезали навсегда, каждый диалог становился пустым. Регистрации идемпотентны по построению
(`RegisterAction`/`RegisterTag` перезаписывают по имени), поэтому повторный прогон безопасен.

**Своих формулировок не добавляем.** Всё, что видит игрок, берётся из пулов
`SR_2_HD_Lang_vanilla`. Служебные кнопки — общие пулы: `Accept` «Согласен», `Reject`
«Отказываюсь», `Cancel` «Отмена», `Exit` «Конец связи», `To` «-->» (префикс строки списка
и кнопка «продолжить»). Если для нужного пункта в Lang строки нет — значит в оригинале такого
пункта не было: у транклюкатора, например, нет приказа о гиперпрыжке, и мы его не выдумываем.

## 6. Командные диалоги партнёров

Три роли говорят разными голосами, и путать их нельзя — пулы под каждую свои:

| диалог | пулы | кто |
|---|---|---|
| `Ship_Drone_default` | `Tranclucator.*` | боевой робот-компаньон («хозяин») |
| `SpaceTalk_PartnerOrders` | `Partner.*` | наёмный рейнджер/воин/транспорт («босс») |
| `SpaceTalk_PirateOrders` | `Pirate.*` | наёмный пират («шеф», «братан») |

Маршрутизация — в `Ship_default/intro` по `ship_type`: пиратский партнёр уходит в
`SpaceTalk_PirateOrders`. Каждый приказ проходит через узел подтверждения: `ComputerAgree*` при
согласии либо `ComputerDisagree*`/`ComputerInFear` при отказе. Отказ реален — приказы живого
партнёра проверяются через `DisciplineCheck.ShouldObey(…, PartnerOrder)`, результат кладётся в
`ctx.Data["order_obeyed"]`, и узел выбирает реплику по нему. Дрон — механизм, он не спорит.

Реплики разрыва контракта берутся из пулов в `PartnerService.Break`: `Partner/Pirate.MateTheEnd`
(срок вышел), `MateRiot` (бунт), `MateBreak` (уволен игроком).

### Разрешения подчинённого

Подменю «Настроить поведение» (`Tranclucator.Options.*`) — три тумблера на `ShipData`. Значение по
умолчанию `true`, поэтому сейвы без этих полей ведут себя как раньше.

| флаг | что запрещает | где гейт |
|---|---|---|
| `AllowCollect` | самому подбирать вещи | `NpcBrain.DecideMercenaryDefault` не выдаёт `ActionScavenge`; выключается и `AutoPullActive` |
| `AllowLand` | садиться | `ActionPartnerAttend` отбрасывает приказ `OrderLand`, `NpcBrain.ShouldResupply` не уходит на дозаправку |
| `AllowArrange` | переставлять оборудование | `ShipLoadoutService.TickTurn` не вызывает авто-экипировку (разбор перегруза не гейтится — иначе корабль встанет намертво) |

Запрет отменяет уже выданное: снятие `AllowCollect` гасит `AutoPullActive`, снятие `AllowLand`
сбрасывает приказ `LandOn`. Прямой приказ «собирай вещи» флагом не гейтится — это явная воля лидера.

Подменю есть у всех трёх ролей (дрон и оба партнёра): реплика показывает текущее состояние,
клик переключает, подтверждение приходит фразой `Options.*Yes` / `*No`. Названия категорий в
`<Item>`/`<Land>` берутся из пулов `Options.Collect` («Артефакты») и `Options.Land` («Планеты»).

## 7. Приветствия

`PlanetGreetings.Rules` / `ShipGreetings.Rules` — правила матчинга по расе, типу, отношениям,
экономике и т.д. (`GreetingRule`, ~60 полей). Тексты — в `Greetings[Id]` текст-конфига;
`Id` обязателен, иначе правило не получит фраз и промолчит. Выбор — `PlanetGreetingSelector` /
`ShipGreetingSelector`, рендер плейсхолдеров — `PlanetGreetingRenderer`.

Плейсхолдеры приветствий (`<Player>`, `<CurPlanet>`, `<ShipBad>`, …) — **другой синтаксис**, чем
`{теги}` диалогов, и раскрываются своей картой подстановок. Карта засевается нейтральными
значениями из `TextsConfig.Dialog.GreetingDefaults` (ключ — имя плейсхолдера без скобок), а
конкретные данные их перекрывают. Таблица обязана покрывать **все** встречающиеся плейсхолдеры:
непокрытый уедет игроку сырым `<Tag>`, а приветствие показывается при каждом открытии диалога.

## 8. Валидация на загрузке

`DialogConfigValidator.Validate(cfg)` — только warnings, конфиг не блокируется. Проверяет:

- `StartNode` существует; все `NextNode` ведут в существующий узел (пусто/`null` = конец диалога);
- узел не пустой (есть `Text` или хотя бы одна реплика);
- у действия задан либо `Method`, либо `Script`;
- **инлайновые фоллбэки** `{tag|фраза}` — ищутся по началу `{tag|`, а не по полному шаблону:
  регэксп с `[^{}]*` (как и сам `Substitute`) слеп к вложенным тегам, и узел с
  `{pool:X|Атакую «{target}»}` показывал игроку литерал со скобками;
- **`{pool:Key}` ведёт к живому пулу** или к дефолту (для шаблонных ключей — хоть одно совпадение);
- **синтаксис Lua** в `lua:`-условиях и `Script` — компиляцией. Без этого опечатка проявлялась бы
  только в рантайме: условие даёт false, и реплика молча исчезает из списка;
- у каждого правила приветствия есть `Id` и непустые тексты.

## 9. Известные ограничения

- `TagDefaults`/`Speakers` — единственное значение на тег/диалог. Если одному тегу нужны разные
  фразы в разных узлах, вариантов два: отдельный тег или отдельный ключ пула (так разведены
  корабельные и станционные сплетни — `Gossip.Station`).
- Регэксп тегов не допускает `(`/`)` в имени, поэтому `{lua:Player().Money}` в тексте **не
  сработает** — параметризованный тег `lua` применим лишь к выражениям без скобок. Для сложного
  используй обычный тег-резолвер.
- Пулы не поддерживают вес вариантов — выбор равновероятный.
- `{partner_months}` не имеет дефолта намеренно. Срок = `ContractTermYears × 12` из типа корабля;
  все нанимаемые типы в `PartnersConfig.json` имеют конечный срок (Pirate 1 год, Ranger 2,
  Warrior 3, Transport 5), поэтому тег всегда резолвится. Если добавить тип с `-1` («бессрочно»),
  фразы пулов `Partner.ComputerSayOk` / `Partner.Ok` покажут литерал `{partner_months}`: они
  построены вокруг числа («работать на тебя `<Month>` мес.»). Это осознанно — видимый тег укажет
  на причину, тогда как подставленное число соврало бы про правила игры. Тогда либо задай тому
  типу конечный срок, либо перепиши эти строки под бессрочный контракт.
- Некоторые исходы не имеют реплики в конфиге и потому не показываются игроку:
  `incoming_rob`/`incoming_extort` → `ShipRefuses`, `incoming_extort` → `SumIsVeryBig`.
  Механика при этом отрабатывает, просто без ответной фразы.
- Не подключено (22 пула из 316):
  - `Attack.*Send`, `Attack.ComputerReadyAttack` (8) — NPC сам предлагает игроку напасть вместе.
    Нужен входящий диалог по образцу `Ship_incoming_*` плюс триггер в ИИ.
  - `Partner/Pirate.AnswerLider*` (6) — ответ игрока на то, что партнёр объявил о разрыве.
    Разрыв сейчас происходит вне диалога (сообщение в консоль), отвечать некому.
  - `Partner/Pirate.Send` (2) — «Я готов выложить `<Money>` cr за то, чтобы ты стал партнёром»:
    альтернативная формулировка предложения. В схеме (§9) торг начинается с `[PlayerSend]` из
    главного меню, а `Send` в поток не входит — вставлять его значило бы дублировать пункт.
  - `Pirate.AttackShip` (1) — строка списка целей «`<ShipName>`». Непригодна: `<ShipName>`
    резолвится в цель диалога (самого пирата), а не в строку списка; список показывает имя
    тегом `nav_atk_*_name`.
  - `Accept` / `Reject` / `PlanetSay` / `ShipSay` (4) — метки UI, которым в текущих деревьях
    не нашлось места.
- Схемы SR2HD `MilitarySupport`, `ExTalk`, `Female`, `PirateClan` не реализуются намеренно.
