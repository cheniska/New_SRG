================================================================================
 Компаньоны игрока: партнёры и транклюкаторы
 (game-design реконструкция, без привязки к платформе)
================================================================================

Статья описывает две принципиально разные модели «спутника» игрока в
космической RPG-игре и предназначена как спецификация для воссоздания
механик с нуля. Термины «корабль», «звезда», «планета», «станция»
трактуются абстрактно; конкретные формулы, пороги, ветки решений и
диалоговые команды приводятся полностью.

Две модели:

  А) ПАРТНЁР — самостоятельный NPC (рейнджер или пират), временно
     подчинённый игроку по контракту; сохраняет собственную личность,
     AI и репутационную систему; можно уговорить, нанять, дать команду,
     оплатить, расторгнуть контракт.

  Б) ТРАНКЛЮКАТОР — искусственный корабль-компаньон, покупаемый как
     товар; всегда подчинён владельцу, живёт в двух формах (летающий
     корабль и предмет инвентаря), никаких переговоров и репутации —
     чистый «инструмент» с прикладными командами.


================================================================================
 ЧАСТЬ I. ПАРТНЁРЫ (рейнджер и пират)
================================================================================

--------------------------------------------------------------------------------
 1. Модель данных
--------------------------------------------------------------------------------

На каждом корабле хранится пара полей, описывающих партнёрство:

    PartnerLeader  — ссылка на «босса» (nil, если корабль свободен).
    PartnerDays    — счётчик оставшегося срока контракта. Используется
                     только для одного пути найма (см. §3.2); при нуле
                     партнёр самостоятельно расторгает контракт.

Точку зрения проще держать зеркально: «у моего партнёра поле
PartnerLeader указывает на меня». Босс не хранит массив партнёров как
основную структуру — при необходимости он пересчитывается сканированием
всех кораблей мира. Однако у босса-игрока имеется вспомогательный
список персонально для пиратов-клан-подчинённых (см. §3.2) — его нужно
поддерживать в синхроне.

Скриптовое (модовое) API должно уметь:
  * Читать/писать пару (PartnerLeader, PartnerDays) на любом корабле.
  * Перечислять все корабли-партнёры данного босса по всему миру.
  * При SetPartner(new_leader) синхронизировать вспомогательный список
    пирата-клана: если старый босс == Player и корабль — пират, удалить
    из FPirates; если новый босс == Player и корабль — пират, добавить.

Индексаторы (используются в диалогах и AI):

    CountPartnersInGalaxy(boss)
        = число кораблей во всём мире, у которых PartnerLeader == boss.
        Смысл: «сколько у меня всего подчинённых».

    CountPartnersInMyStar(boss)
        = среди кораблей текущей звезды, где PartnerLeader == boss И
          корабль CanAct (не на посадке/прыжке/уничтожен).
        Смысл: «сколько сопровождающих меня прямо сейчас в системе».
        Используется чтобы решить, показывать ли команду «приказ всем»
        (>1 партнёр в системе).


--------------------------------------------------------------------------------
 2. Приглашение партнёра-рейнджера через диалог
--------------------------------------------------------------------------------

Игрок начинает диалог, выбирает «предложить партнёрство». Проверки идут
последовательно, первый провал = отказ, дальше не проверяется:

    (1) Отношение цели к игроку >= 45  ────► «Talk.Partner.Suspect»
    (2) target.PartnerLeader == nil    ────► «AlreadyHavePartner»
    (3) CountPartnersInGalaxy(target) == 0
                                       ────► «ILeader»
        (у собеседника уже есть свои подчинённые — он «самостоятельный
         лидер», в чужую команду не пойдёт)
    (4) Player.Skill_Leadership > CountPartnersInGalaxy(Player)
                                       ────► отказ по перегрузке лидерства
    (5) target.Rank <= Player.Rank     ────► «YouNeedInMoreRank»

Если все прошли — стороны торгуются о цене (единовременная оплата).

Стартовое предложение хранится в глобальной переменной сессии диалога
(«текущее предложение»). Функция ComputePartnerFee(target, offer, player)
возвращает 0 (не согласится) или money>0 (согласится за money):

    Если offer < target.PathTotal / 45  → return 0
    (target.PathTotal — сколько всего налетал корабль; ниже минимума
     он не пойдёт ни за какие деньги, потому что «дешевле — оскорбление»).

    Иначе:
        base           = PortionInDiapason(36, 8, PathTotal/8, PathTotal/45, offer)
        attitudeFactor = PortionInDiapason(1.5, 0.7, 100, 50, attitude)
        money          = round(base * attitudeFactor)
        if Player.Skill_Charisma is at max: money *= 2
        return money

Функция PortionInDiapason(y_hi, y_lo, x_hi, x_lo, x) — стандартная
линейная интерполяция с зажатием на границах диапазона.

Диалог показывает игроку:
  * «ComputerSayOk» — если money>0 (согласен за money).
  * «ComputerSayNo» — если 0.
  * «PlayerLess»  — предложить меньше (offer /= 2), пересчитать.
  * «PlayerMore»  — предложить больше (offer *= 2), но не выше баланса.
  * «PlayerOk»    → SetPartner(target, Player), звук, конец. Деньги
                    списываются с игрока и записываются на партнёра.
  * «Cancel»      — отмена.

В этом пути найма PartnerDays НЕ выставляется — контракт висит
бессрочно, пока одна из сторон не расторгнет.


--------------------------------------------------------------------------------
 3. Приглашение партнёра-пирата — два пути
--------------------------------------------------------------------------------

3.1 Через диалог с диким пиратом (одиночный найм)

Дополнительно к пяти общим проверкам:

    * CountExistingPartnersOfBoss(Player) > Player.BridgeCapacity
      → «NeedPirate».
      CountExistingPartnersOfBoss — не обычный счёт партнёров, а
      «взвешенный»: считаются фиктивные слоты, чтобы более уважаемые
      пираты «занимали больше места на мостике». Формула счёта у босса:
          1  если Player.PirateRank > 60
          +1 если Player.PirateRank > 75
          +1 если Player — «Eminent Ranger» (высшая звёздная награда)
          +1 если Player.Rating > 0

      Player.BridgeCapacity — техпараметр мостика игрока (или его
      эквивалент; фактически ограничивает свиту).

    * Если Player.Owner == PirateClan И target.PirateRank > Player.PirateRank
      → «NeedPirate». Пират не подчинится тому, кто ниже него в клане.

Дальше та же ComputePartnerFee и та же торговля. При PlayerOk:
    SetPartner(target, Player)
    Player.FPirates.Add(target)  ← синхронизация клан-списка

Срок службы не задаётся.

3.2 Через Construct Base (пиратскую конструкторскую базу)

Работает только когда игрок — глава пиратского клана. На пиратской базе
игрок «собирает» нового пирата под заказ:

  Шаги:
    1. Игрок выбирает оснащение — 8 слотов equipment + до 5 артефактов.
       Считается суммарная стоимость cost.
    2. Player.Money -= cost.
    3. Создаётся новый TPirate, добавляется в текущую звезду.
    4. Копируется выбранное оснащение и артефакты в новый корабль.
    5. Инициализация пирата: money = cost/10 + 1000, стартовые статы.
    6. newPirate.CurRuins := player.CurRuins (стартует сразу на базе).
    7. newPirate.SetReputationToward(Player) := 100 (лояльность максимум).
    8. Если Player.FPirates.Count < BridgeCapacity:
           newPirate.PartnerLeader := Player
           newPirate.PartnerDays   := 30 * ComputePartnerFee(...)
           Player.FPirates.Add(newPirate)
       Иначе — показать «мостик полон», найм отменяется.

Именно этот путь даёт тикающий счётчик срока службы (в среднем несколько
десятков дней). Только по CB-найму партнёр в перспективе сам уйдёт.


--------------------------------------------------------------------------------
 4. Как партнёрство меняет AI: РЕЙНДЖЕР
--------------------------------------------------------------------------------

Партнёр-рейнджер — активный wingman. Его ежедневный AI («daily
decision») получает флаг «у меня есть босс» и в ветке in-space (не на
планете, не на станции) строит поведение так:

  (1) СИНХРОНИЗАЦИЯ ЦЕЛИ С ЛИДЕРОМ.
      Если у лидера есть текущий бой (leader.CombatTarget != nil) и
      лидер движется к нему (leader.DestObj == leader.CombatTarget),
      и мой квест-флаг активен:
          self.CombatTarget := leader.CombatTarget
          Engage(self.CombatTarget)  → атакуем ту же жертву.
      Если у меня есть свой CombatTarget и он «враг игрока»
      (Relation(target, Player) != 0), и я могу действовать → Engage.

  (2) ОТМЕНА ЛОЖНОГО КУРСА.
      Если я в state=Follow и мой DestObj не совпадает с DestObj лидера
      И цель не враг Player → ChangeState(0), сбросить.

  (3) ПРИОРИТЕТЫ ВОЗВРАТА К ЛИДЕРУ.
      Если у меня нет активного приказа И выполнено любое из:
          * Я в безопасном состоянии И полученный XP > нужного для
            следующего уровня (нужно апнуться, а рядом лидер — иди к
            нему).
          * Здоровье < критический порог (нужен ремонт).
          * MB_TShip_GetHealthPercent < 70% И рядом валидная цель
            (нужен щит спины).
      → GoToLeaderOrNearest.

  Функция GoToLeaderOrNearest — сердце follow-логики:

      Если leader есть, но НЕ в моей звезде:
          Если leader сейчас в state=Approach к другой звезде
              → OrderApproachTarget(leader.DestObj)
                (я прыгаю прямо туда, куда он).
          Иначе → OrderApproachTarget(leader.CurStar)
                (я прыгаю к нему в текущую звезду).

      Если leader в моей звезде:
          Если я в state=Landing И DestObj == leader.DestObj:
              оставить как есть.
          Если leader в state=Landing (садится на планету/станцию):
              Проверить «мне НАДО остаться в космосе»:
                  * нужна станция (флаг «Need base»)
                  * safe state + XP overflow
                  * target — станция, и через её правила можно войти
                  * низкий hull
                  * рядом враг, которого нужно добить
              Если ХОТЯ БЫ ОДНО совпало И станция позволяет вход:
                  → OrderLandToTarget(leader.DestObj) — сесть туда же.
          Если leader в state=Approach:
              → OrderApproachTarget(leader.DestObj).

      Иначе (нет leader либо он в моей звезде и не помог):
          Fallback-поиск (в порядке приоритета):
              1) ближайший невраждебный корабль в системе;
              2) ближайшая доступная станция (по её правилам входа);
              3) в радиусе гиперпрыжка — ближайшая дружественная звезда.
          Приоритет по нормированному расстоянию.

  Итог: рейнджер-партнёр всегда «тянется» к лидеру. Между делом — свои
  миссии, свои бои, сам летит починиться.

Дополнительно: на планете партнёр-рейнджер снимает часть «задержек
перед взлётом» (пусть быстрее уходит следом за лидером); каждые ~50
игровых дней проверяет своё отношение к боссу (опционально приводит к
уходу, если отношение упало).


--------------------------------------------------------------------------------
 5. Как партнёрство меняет AI: ПИРАТ
--------------------------------------------------------------------------------

Пират-партнёр архитектурно ДРУГОЙ. Ключевой внутренний флаг:

    isRealPirate = (ClassStatus[1] > 0  И  Owner == PirateClan)

Наёмник, отработавший на игрока-рейнджера, теряет клановую
принадлежность → isRealPirate = false, и он действует как «наёмник».
Пират, нанятый игроком-клан-лидером через CB, сохраняет
Owner==PirateClan → isRealPirate = true, продолжает быть «настоящим
пиратом», просто в иерархии.

Ветка 1 — isRealPirate=true, есть PartnerLeader:
    Ведёт обычную «работу пирата»: PickAggroTarget, посадка на
    пиратские станции, сбор на Construct Base при 3+ бесхозных пиратах
    рядом, роумит рандомом. Работа «по лидеру» минимальна — только «если
    лидер вошёл в звезду с Owner=Pirates ИЛИ вошёл в непиратский
    контекст» слегка сдвигает предпочтения.

Ветка 2 — isRealPirate=false, есть PartnerLeader:
    Это пират-наёмник рейнджера. Тактика более мирная:
      * Если активен внутренний квест-флаг:
          - 30% шанс: посадка на набор пиратских типов станций.
          - Иначе: 50% на «сесть на ближайшую» / «сесть на назначенную».
          Если меня преследует ranger/warrior И я близко к нему И я
          не оторвался — 30% на выкуп грузом (TryDropGoodsAsRansom),
          но только по чётным дням (чтобы не спамить).
      * Если квест-флага нет:
          - Внутренняя обработка (перегруппировка).
          - Если лидер близко (в моей планетной зоне) — ничего не делаю.
          - Если XP overflow — сесть на станцию апать скилл.
          - Обычный roam/engage.
          - Без приказа и без квест-флага → JumpToFreshSystem (уйти).
          - Без приказа → PursueAggroTarget (искать добычу).

КРИТИЧНОЕ ОТЛИЧИЕ ОТ РЕЙНДЖЕРА: у пирата в daily AI НЕТ прямой
follow-логики «прыгаю за лидером в его звезду». Пират-подчинённый
действует как обычный пират, но с меньшей агрессией к преследователям
и с приоритетом «уйти на пиратскую станцию» при XP-overflow. Никакого
активного wingman-режима.

Единственный способ синхронизации курса пирата с лидером — прямые
приказы из диалога (см. §6).


--------------------------------------------------------------------------------
 6. Диалоговые команды партнёру
--------------------------------------------------------------------------------

Когда игрок разговаривает с кораблём, у которого PartnerLeader == Player,
диалог расширяется. Меню одинаково и для рейнджера, и для пирата.

6.1 Атаковать конкретную цель (сфокусированный приказ)

  Из списка кораблей текущей звезды выбираются кандидаты:
    * дистанция от игрока <= Player.RadarRange;
    * не сам игрок, не лидер, не сам партнёр;
    * не станция (тип < некоторого порога);
    * цель «угрожает игроку» (внутренняя проверка);
    * цель НЕ имеет состояния «дипломатически защищена».
  Для каждого — пункт «Атаковать <name>». По выбору:

    SetPairedCombatTarget(partner, Player, target):
        partner.CurCombatTarget := target
        Player.CurCombatTarget  := target
        Для всех weapons партнёра — lockedTarget := target
        (если у оружия хватает reach)
        Player.AutoBattleShip := target (переход в бой)
        OrderFollowShip(partner, Player, tFollowAttack=1, absolut=1)

  Дополнительно предлагается «OrderForAll» (см. §6.3), если у игрока в
  системе >1 партнёров.

6.2 Одиночные приказы

  «Fly to me»       → OrderFollowShip(partner, Player, tFollowNear=0, absolut=1)
  «Land on object»  → OrderLandToTarget(partner, Player.DestObj, absolut=1)
                      (сесть туда же, куда сейчас летит игрок)
  «Fly to Star»     → OrderApproachTarget(partner, Player.DestObj_as_Star, absolut=1)
                      (прыжок в назначенную игроком звезду)
  «Drop cargo»      → бросить весь груз в космос:
                        - Если !HasRelation(partner, Player):
                              partner.Reputation -= 10 (штраф лояльности)
                        - Если partner.HasCargoRoom > 0: DropAllCargoToSpace;
                          показать «ComputerDropCargoOk».
                        - Иначе «ComputerDropCargoNo».

6.3 OrderForAll — раздать приказ всем партнёрам в системе

  Для каждого корабля в Player.CurStar, у которого PartnerLeader == Player,
  CanAct, не сам игрок и не уже приказанный ранее в этом диалоге:

        switch (Player.State):
            case Landing:   OrderLandToTarget(ship, Player.DestObj)
            case Approach:  OrderApproachTarget(ship, Player.DestObj_as_Star)
            case Follow:    SetPairedCombatTarget(ship, ship, Player.CombatTarget)
            default:        OrderFollowShip(ship, Player, tFollowNear=0)

6.4 Финансы и подарок

  «Финансовый отчёт»: партнёр отчитывается сколько накопил (money).
    Если Player.Money > 0 — доступна опция «предложить подарок».

  «Подарок»: игрок выбирает сумму (стартово — глобальный параметр
    сессии). Кнопки Less/More/SendGift/Cancel аналогично торговле за
    контракт. При принятии:

        Reputation_boost = 176 (базовый) + рост от pathTotal:
            v20 = target.PathTotal_extra + Player.PathTotal
            v21 = clamp(v20 / N, 0..100)   ← масштаб-коэффициент по «стажу»
        target.Reputation_toward(Player) += Reputation_boost
        (плюс более тонкое масштабирование на v21 в диапазоне 0..100 при
         взаимных «делах», для «уважения выше среднего»)
        Player.Money -= amount
        target.Money += amount
        Проиграть звук + строку «FinancesGotGift».

  Смысл — единственная механика, позволяющая повышать привязанность
  партнёра, у которого нет тикающего срока. Регулярно давать подарки =
  замедлять естественное падение привязанности.


--------------------------------------------------------------------------------
 7. Разрыв связи
--------------------------------------------------------------------------------

Партнёрство завершается по трём сценариям:

  * Инициатива игрока: диалог «BreakPartner» (строки MateBreak/
    AnswerLiderBreak). Прямо снимает PartnerLeader.
  * Инициатива партнёра по сроку: PartnerDays <= Galaxy.Day → уходит
    (только для CB-найма). Реплика зависит от Player.Skill_Leadership:
    Standard «MateTheEnd» или «MateTheEndLowLeadership».
  * Riot: партнёр расторгает контракт из-за низкой репутации или
    переполненного лидерства. Строки «MateRiot/AnswerLiderRiot».

При SetPartner(nil) обязательно:
  * Если корабль был TPirate И старый босс == Player: удалить его из
    Player.FPirates.
  * Если корабль был TPirate И новый босс == Player: добавить в
    Player.FPirates.

Скриптовый API SE_ShipSetPartner делает эту синхронизацию автоматически.


--------------------------------------------------------------------------------
 8. Итог по партнёрам: рейнджер vs пират
--------------------------------------------------------------------------------

По приглашению:
  Рейнджер — только диалог AskJoin. Отказ если у него уже есть
             подчинённые. Цена — по ComputePartnerFee.
  Пират    — диалог AskJoin (требует Player.PirateRank >= пирата) ИЛИ
             Construct Base (Player как глава клана). CB-путь даёт
             тикающий срок ~30 × ценовой-параметр.

По AI:
  Рейнджер — активный wingman. GoToLeaderOrNearest тянет к лидеру,
             перехватывает CombatTarget лидера, прыгает следом.
  Пират    — если Owner==PirateClan остался — «пират в иерархии, но
             сам». Если стал наёмником рейнджера — умеренная агрессия,
             посадка на станцию, отдаёт грузом при перегоне. Активной
             follow-логики нет ни в одном случае.

По приказам из диалога: идентично.
По подарку: идентично.
По разрыву: оба поддерживают все три сценария.


================================================================================
 ЧАСТЬ II. ТРАНКЛЮКАТОР (искусственный компаньон)
================================================================================

--------------------------------------------------------------------------------
 9. Идея класса
--------------------------------------------------------------------------------

Транклюкатор — уникальный NPC-корабль-помощник, купленный как товар в
магазине планеты. От партнёра отличается принципиально:

  * У него нет собственной AI-жизни: он полностью служит владельцу.
  * Живёт в ДВУХ формах:
      (i)  ship — летающий корабль в звёздной системе;
      (ii) artefact — предмет в инвентаре владельца.
    Каждая форма может быть развёрнута в другую по команде.
  * Использует НЕ поле PartnerLeader, а собственное поле Owner.
  * Не платит зарплату, не имеет срока службы, не имеет «настроения» и
    не может уйти сам.
  * По команде «свернуться в инвентарь» ← ключевая механика — заодно
    выгружает игроку весь груз, что нашёл в бою/собрал.

Это чистый tool-companion в противовес RPG-companion (партнёр).

--------------------------------------------------------------------------------
 10. Данные транклюкатора
--------------------------------------------------------------------------------

Базовые ship-поля: обычные (CurStar, CurPlanet, State, CurCombatTarget,
Engine, weapons, cargo и т.п.). Специфичные:

    Owner              — указатель на владельца (в норме — TPlayer).
    Cmd_AttackTarget   — байт-флаг: «участвуй в бою вместе с Owner».
    Cmd_CollectItems   — байт-флаг: «собирай items с поля».
    Cmd_FullAutonomy   — байт-флаг: «сам обслуживай оружие/защиту».
    Cmd_ReturnNow      — байт-флаг: «свернись в артефакт при первой
                          возможности».

Битмап-фильтр предметов (что собирать):
    Filter_Slot        — bitmap стандартных слотов оснащения,
                         которые разрешено брать (default-слоты).
    Filter_Artefact    — брать TArtefact.
    Filter_MicroModule — брать TMicroModule.
    Filter_Default     — брать default-slot items.
    Filter_Useless     — брать TUselessItem.
    Filter_Goods       — брать TGoods.
    Filter_Countable   — брать TCountableItem.
    Filter_LandMask    — где разрешено садиться для разгрузки:
                         bit 0 = allow planet, bit 1 = allow station.


--------------------------------------------------------------------------------
 11. Спавн — три способа создания
--------------------------------------------------------------------------------

11.1 Покупка в магазине планеты

    tran := TTranclucator.Create
    tran.Init(nil, planet.Owner, small_flag)
        // small=0: полный корабль (Hull/Engine/Weapon/DefGen/RepairRobot/CargoHook)
        // small=1: упрощённый (без обслуживания)
        // Оснащение подбирается на базе AvgSize-таблиц и глобальных
        // технологических уровней (GTL) галактики.
    tran.CurPlanet := planet
    tran.CurStar   := planet.Star
    planet.Star.Ships.Add(tran)

11.2 Из артефакта в инвентаре (SE_UseTranclucator)

  В инвентаре игрока Транклюкатор хранится как TArtefactTranclucator —
  особый предмет-контейнер, внутри которого лежит «упакованный» ship со
  всеми его характеристиками.

  UseTranclucator(player, [artefact]):
    Если artefact не задан — берётся первый неиспользованный из
    player.ArtefactItems.
    ship := artefact.packed_ship
    ship.CurStar := player.CurStar
    star.Ships.Add(ship)
    Если ship.CanAct — поставить рядом с игроком: рандомный угол в
                        360°, дистанция = 100 от Player.Pos.
    Если Player.CurPlanet: ship.CurPlanet := Player.CurPlanet
    Если Player.CurRuins:  ship.CurRuins  := Player.CurRuins
    ship.Owner := Player
    Удалить артефакт из инвентаря (ArtefactItems, EquipmentItems) и
    освободить его.
    ship.CalcParam(rebuild)
    post-spawn hook на ship
    return ship

  Т.е. артефакт превращается обратно в летающий корабль-компаньон, с
  сохранёнными характеристиками. Груз при упаковке — уже был передан
  игроку (см. §14).

11.3 Через скриптовый API мода — вызывается тот же BuyTranclucator.


--------------------------------------------------------------------------------
 12. Главный AI-цикл (ежедневный)
--------------------------------------------------------------------------------

Транклюкатор запускает свой DailyDecision. Дерево решений:

  (1) PRECONDITION:
      Если нет Engine ИЛИ нет NavData → OnNoNav_Cleanup
      (очистить orders, сбросить state — «безмоторный», ждать).

  (2) АВТОНОМИЯ:
      Если Cmd_FullAutonomy ИЛИ Owner == nil:
          AutoEquipSlots       (сам выбирает лучшее оснащение из имеющегося)
          StockUpEquipment     (докупить/пополнить)

  (3) VMT+96 (пост-этап tick для weapons/repair — оставим абстрактно).

  (4) РАЗВЕТВЛЕНИЕ ПО КОНТЕКСТУ ВЛАДЕЛЬЦА:

      (4a) Владелец на планете ИЛИ в trade-контракте
           (внутренние вспомогательные проверки MB_PlayerIsOnPlanet /
            HasTradeContracts2):

           Если Cmd_ReturnNow: попытаться свернуться в артефакт
                 (см. §14). Если не получилось — упасть в FlyToOwner.
           Иначе → FlyToOwner:
               Если overloaded (free_space < 0):
                   HandleOverload → сброс низкоценного груза;
                   если стало ок → OrderJump_BuildTrajectory (взлёт);
                   иначе → упаковаться в артефакт (форс-компакция).

      (4b) Владелец в системе, свободен:
           Если CanAct:
               VMT+32 (боевой tick)
               Если не перегружен:
                   * Cmd_CollectItems И free_space > 0:
                       PickupItems (см. §13.2)
                       ИЛИ LandOnFriendly (сгрузить на дружелюбную
                       планету/станцию, если перегружен по факту).
                   * Cmd_AttackTarget И есть Owner:
                       OrderFollowShip(Owner, tFollowNear=0)
                       — следовать вплотную; в бою — вступать в пару.
                   * Иначе (и не в специальном idle-state):
                       FollowOwnerOrTarget (см. §13.1).
               Иначе (перегружен):
                   HandleOverload.


--------------------------------------------------------------------------------
 13. Подмодули AI
--------------------------------------------------------------------------------

13.1 FollowOwnerOrTarget — базовый wingman

  Приоритеты (первое сработавшее — конец):
    (1) У меня есть CurCombatTarget, он в моей звезде, он CanAct
        → OrderFollowShip(target, tFollowAttack=1). Иду добивать.
    (2) Owner в моей звезде, CanAct:
        * Если Owner в state=Follow И Owner.CurCombatTarget ==
          Owner.DestObj (то есть Owner активно преследует врага) И его
          жертва — не я сам:
              OrderFollowShip(Owner.CurCombatTarget, tFollowAttack=1)
              — перенимаю бой Owner'а.
        * Иначе:
              OrderFollowShip(Owner, tFollowNear=0)
              — просто иду за ним.
    (3) Owner в моей звезде, но Owner.CurPlanet != nil (садится):
              OrderMove_Internal к planet.orbit_pos
              — иду на ту же орбиту.
    (4) Fallback: случайный roam.

13.2 PickupItems — сбор трофеев с поля

  Требования: CargoHook работает, скорость > 0, есть место в трюме.

  Итерация по всем items в CurStar:
    Пропустить если Item.reserved (уже прицеплен другим).
    Проверить, что CargoHookPower >= Item.mass (крюк тянет).
    Пропустить если не проходит по типу-фильтру:
        TArtefactTranclucator (сам такой тянуть не нужно) — фильтр всегда on
        TGoods            → Filter_Goods
        TArtefact         → Filter_Artefact
        TMicroModule      → Filter_MicroModule
        TCountableItem    → Filter_Countable
        TUselessItem      → Filter_Useless
        default-slot item (номера слотов 43..67) → Filter_Slot
        обычный slot      → Filter_Default
    Пропустить если fee-check > 0 (стоимость выше моего бюджета).
    Проверить, что (free_space - already_reserved) >= item.mass.
    Если ProcessInventory сумел взять сразу — mark + продолжить.
    Иначе — измерить квадрат расстояния до item; если ближе прежнего
      и по скорости успеваю — запомнить как best.

  По итогу:
    Если найден best → зарезервировать + OrderMove_Internal к нему.
    Если ничего не найдено и я в state=Idle → ChangeState(0).

13.3 LandOnFriendly — разгрузка при перегрузе

  Транклюкатор нашёл, куда сесть и высыпать груз:
    Если Filter_LandMask содержит planet-bit: искать планеты с
      Owner < 5 (нейтралы/дружеские фракции) ИЛИ Owner == PirateClan,
      И RelationCategory >= 2 (нейтралы+).
    Если Filter_LandMask содержит station-bit: искать станции TRuins с
      Relation_to_Player >= 2 И правило-станции разрешает вход.
    Из подходящих — ближайший по dist² → OrderLandToTarget.

13.4 FlyToOwner — доставка груза владельцу

  Владелец в оседло-состоянии (на планете / в контракте). Действия:
    Если Player.CurPlanet:
        TransferCargoToOwner(planet)
            — весь трюм переливается в inventory игрока прямо на планете.
        Если free_space >= 0: OrderJump_BuildTrajectory (взлёт).
        Return 1.
    Если Player в trade-контракте (текущий контракт):
        TransferCargoToOwner(contract)
            — груз идёт получателю контракта.
        Если free_space >= 0 И CanAct(contract-target):
            OrderJump_BuildTrajectory.
        Иначе: ChangeState(0).
        Return 1.

  Т.е. режим «прилететь, отдать, снова свободен».


--------------------------------------------------------------------------------
 14. Упаковка обратно в артефакт (ReturnAsArtefact)
--------------------------------------------------------------------------------

Ключевая уникальная механика Транклюкатора. Транклюкатор буквально
«схлопывается» в предмет инвентаря.

Предусловие: Player сейчас на планете (Owner<5 или ==PirateClan) или в
активном контракте — только там можно свернуться.

Этапы (в порядке):

  (1)  Cmd_ReturnNow := 0
       Cmd_CollectItems := 0
       Cmd_AttackTarget := 0
       (снимаются все команды).

  (2)  CurCombatTarget := 0
       (внутренний _3F8 «блок кооперации» := 0)
       AssignedTask     := 0
       (сброс всех сцепок с другими кораблями).

  (3)  ChangeState(0)
       NextDayLogic := 0
       (сброс поведенческих флагов).

  (4)  Для каждого weapon-слота: target_lock := 0.

  (5)  Если есть скриптовое привязывание (TScriptShip) — отвязать.

  (6)  Удалить себя из CurStar.Ships (TList_Delete).

  (7)  CurStar := 0
       CurRuins := 0
       CurPlanet := 0
       (корабль исчезает из мира).

  (8)  Engine.fuel := 100
       (полный бак — вернувшись из артефакта, корабль снова готов
       летать).

  (9)  TransferCargoToOwner(destination)
       — весь груз в inventory игрока.

  (10) Создать TArtefactTranclucator(race = self.hull.race)
       artefact.PackShip(self)  ← ship упаковывается в артефакт по offset
                                  (сохраняются все характеристики).

  (11) TransferItemToOwner(Player, artefact, destination, slot=-1)
       — предмет вкладывается в инвентарь игрока (в первый свободный).

  (12) Player.CalcParam (пересчёт статов Player'а — стал тяжелее).

  (13) post-spawn hook (VMT+24).

  (14) Диспетчерский event ProcessMissileHit(self, event_type=46,
       artefact, 0, destination). Event 46 = «Транклюкатор вернулся»,
       обрабатывается скриптами (например, для достижений или квестов).
       Тот же event шлётся на Player.

После этого летающего Транклюкатора больше нет — есть только предмет
TArtefactTranclucator в инвентаре, готовый к SE_UseTranclucator для
повторного развёртывания. Все статы, все ремонтопригодные слоты и
топливо сохранены; корабль вернулся «в упаковке».


--------------------------------------------------------------------------------
 15. Диалоговые команды (Talk_Tranclucator_*)
--------------------------------------------------------------------------------

Транклюкатор всегда доступен для разговора — это фактически
интерфейс управления. Меню:

    Collect     — тумблер бит-фильтра типов item (артефакты /
                  микромодули / слоты / товары / прочее). Многопозиционно.
    Land        — тумблер бит-маски посадочных объектов (планета/станция).
    Arrange     — Cmd_FullAutonomy: 1 = сам чинится/оснащается,
                                   2 = не заниматься.
    PlayerBack  — выход.

Отдельные быстрые команды (пункты меню):

    FlyToMe          — прилететь ко мне (OrderFollowShip near-me).
    Return           — свернуться в артефакт (Cmd_ReturnNow := 1).
    SeekItems / SeekItemsCancel — Cmd_CollectItems on/off.
    DropCargo        — сбросить весь груз в space.
    LandOnObject     — сесть на объект по выбору.
    LandOnStorage    — сесть на «планету-хранилище».
    OrderForAll      — раздать команду ВСЕМ транклюкаторам игрока.

У Транклюкатора собственный список у игрока (PlayerTranclucators),
доступен через скриптовое API — точнее, скриптовый enumerator по всем
кораблям владельца.


--------------------------------------------------------------------------------
 16. Разница «Партнёр vs Транклюкатор»
--------------------------------------------------------------------------------

    Аспект                     | Партнёр (Ranger/Pirate)   | Транклюкатор
    ---------------------------+---------------------------+------------------
    Хранение «лидера»          | PartnerLeader             | Owner
                               | (общее поле на TShip)     | (собственное поле)
    Способ найма               | Диалог AskJoin +          | Покупка в магазине
                               | торговля за оплату        | планеты (обычная
                               |                           | цена товара)
    Срок службы                | PartnerDays (только для   | нет — постоянный
                               | CB-найма пирата)          |
    Регулярная плата           | нет; только подарки       | нет
    Собственная AI-жизнь       | да (свои миссии,          | нет — служит
                               | торговля, бои)            | владельцу
    Список у Player'а          | FPirates (только пираты)  | PlayerTranclucators
                               |                           |
    Может уйти сам             | да (Riot / TheEnd)        | нет
    Своя репутация к рейнджеру | AttitudeList + VMT-логика | тех. переменная
                               |                           | без эффекта
    Свернуться в инвентарь     | нет                       | ДА (уникально)
    Автономная торговля        | да, при пропаже лидера    | нет — не торгует
    Сбор Items с поля          | нет                       | да, bitmap-filter
    Боевой стиль               | Ranger активный wingman;  | Wingman через
                               | Pirate пассивен           | Follow(Owner) +
                               |                           | tFollowAttack
    Регенерация топлива        | обычная                   | 100% при упаковке
                               |                           | в артефакт
    Разрыв связи               | 3 сценария (§7)           | только гибель или
                               |                           | продажа предмета
    Ограничение свиты          | Skill_Leadership          | нет фиксированного
                               | (у босса)                 | (сколько купишь)


--------------------------------------------------------------------------------
 17. Life-cycle Транклюкатора
--------------------------------------------------------------------------------

    (1) Игрок в магазине планеты → BuyTranclucator →
        создаётся TTranclucator + Init + попадает в star.Ships.

    (2) Игрок командует «FlyToMe» → корабль прилетает и висит рядом.

    (3) Летает как wingman через DailyDecision:
          - free_space + Cmd_CollectItems → сбор items;
          - Cmd_AttackTarget → follow Owner в бой;
          - Иначе → FollowOwnerOrTarget.

    (4) Устал/полный трюм: игрок командует «Return» или переставляет
        Cmd_ReturnNow, игрок приземляется:
          → ReturnAsArtefact
          → в инвентаре Player'а появляется TArtefactTranclucator с
            сохранёнными характеристиками ship'а.

    (5) Игрок снова хочет использовать: активирует артефакт в инвентаре
        → UseTranclucator (или UI-хук):
          → извлекает spaceship, ставит рядом с Player.
          → продолжает работу с прежними характеристиками.

    (6) Гибель в бою: обычный TShip.Destroy →
          - Показать GalaxyNews.DeadShip.Tranclucator игроку;
          - Если существовал артефакт в инвентаре Транклюкатора (при
            вложенном сценарии) — он тоже уничтожается.


================================================================================
 ЧАСТЬ III. АРХИТЕКТУРНЫЕ ЗАМЕТКИ ДЛЯ РЕИМПЛЕМЕНТАЦИИ
================================================================================

--------------------------------------------------------------------------------
 18. Ключевые дизайн-принципы
--------------------------------------------------------------------------------

  (A) РАЗДЕЛЕНИЕ «партнёр» и «инструмент».
      Это две ортогональные системы, не пытайтесь свести их к одной.
      Партнёр — это RPG-персонаж с личностью, сроком, лояльностью,
      возможностью бунта. Транклюкатор — это командируемый tool без
      личности. Смешение приводит к двум-в-одном интерфейсу, который
      всегда неудобен.

  (B) ПАРТНЁРСТВО — тонкая обёртка над обычным NPC.
      Это ключ к тому, чтобы механика работала на любом классе NPC без
      переписывания. Ship-класс должен ВСЕГДА иметь поле-указатель на
      «босса»; AI класса должен обрабатывать этот флаг. В коде это
      значит: у каждого класса свой AI, но каждый AI смотрит на общий
      PartnerLeader и меняет свой поведенческий приоритет.

  (C) АСИММЕТРИЯ AI РЕЙНДЖЕРА И ПИРАТА — это фича, не баг.
      Рейнджер как партнёр — активный wingman («полетит за тобой в
      следующую звезду сам»). Пират — самостоятельный: слушается
      диалоговых приказов, но не гонится за тобой автоматически. Это
      выражает разницу «наёмный союзник» vs «попутчик в целях выгоды».

  (D) АРХИТЕКТУРНОЕ ЗАПРЕЩЕНИЕ.
      Определённые классы (доминаторы, наёмные войны фракций,
      транспорт) не должны быть партнёрами. Реализовать через явный
      STUB на слоте hire-check — метод возвращает «Not supporting».
      Диалог AskJoin никогда не появится у таких кораблей. Это чище,
      чем try/if по class-name.

  (E) ТРАНКЛЮКАТОР — принцип «две формы».
      Ship и Item — две ипостаси одного объекта. Реализация:
      * Item (артефакт) содержит указатель на «упакованный» ship-object
        со всеми его данными.
      * Развёртывание = включить ship-object в мир, удалить item.
      * Упаковка   = отключить ship-object из мира, создать item.
      Обе операции требуют выполнения условий (владелец на планете,
      если упаковка). Пропустить условие → сохранять состояние (флаг
      Cmd_ReturnNow ждёт возможности).

  (F) ФИНАНСОВАЯ МЕХАНИКА партнёра — стимул, а не обязанность.
      Подарки повышают репутацию и служат тем «регулятором», которого
      нет у CB-контракта (там срок тикает). Игрок должен ощущать: если
      я не подкармливаю партнёра, он однажды уйдёт по Riot. Это делает
      систему живой без прямого «зарплата за день» — вместо этого
      подарки, которые к тому же поднимают лояльность (репутацию к
      игроку), а значит и AI-помощь.

  (G) ПРИКАЗЫ «ВСЕМ» (OrderForAll).
      Одно и то же действие раздаётся всем партнёрам в системе.
      Реализация — простой цикл: для каждого корабля в CurStar с
      PartnerLeader==Player и CanAct, отдать команду по текущему
      состоянию игрока. Это дёшево и сильно улучшает управление свитой.

  (H) АРТЕФАКТ-КОНТЕЙНЕР.
      TArtefactTranclucator — это generic pattern «предмет-контейнер
      NPC». Аналогично можно упаковывать в предметы, например,
      выпущенных питомцев, туристов, спасённых пилотов и т.д.
      Реализация универсальна: item держит указатель на объект,
      применение возвращает его в мир.


--------------------------------------------------------------------------------
 19. Минимально необходимые типы данных и функции
--------------------------------------------------------------------------------

Для реализации всей описанной системы достаточно:

  Типы:
    TShip                          (базовый корабль)
      + поля PartnerLeader, PartnerDays
      + метод SetPartner(leader) с синхронизацией списков

================================================================================
 20. Резюме
================================================================================

Игра поддерживает две модели «спутника»:

  * Партнёр — «наёмник»/«союзник». Уговоры, торг, репутация, срок
    (условный), возможность бунта, приказы из диалога. Ranger активно
    следует за игроком по звёздам; Pirate — не следует, но слушается
    диалога. Ставится через Talk-найм (общий, с проверками) или через
    CB (только глава пиратского клана, только пират, срок тикает).
    Финансовая связь — единовременная плата за найм и опциональные
    подарки, повышающие репутацию.

  * Транклюкатор — «инструмент». Покупается как товар, полностью
    подчинён владельцу, живёт в двух формах (корабль/предмет). Уникум:
    механика Return-As-Artefact позволяет свернуть его в инвентарь с
    полным сохранением характеристик и переносом груза. Управление —
    через набор диалоговых тумблеров (бит-фильтры сбора, посадки,
    автономии) и одиночных приказов (лететь, сесть, вернуться).

Эти две модели должны сосуществовать: они по-разному обслуживают разные
игровые фантазии — «лидер команды NPC» и «оператор дрон-корабля» — и
не должны быть слиты в одну.
