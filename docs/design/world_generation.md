# Система генерации мира — описание и оценка

## 1. Обзор

`GalaxyGenerator` строит весь игровой мир — от секторов и звёзд до планет, спутников, фракционных границ и стартовых NPC — за один проход по детерминированному сиду. Архитектурно генератор реализован как один **partial class**, разбитый на тематические файлы, что позволяет держать каждый этап в обозримом размере, оставаясь в едином логическом классе.

**Структура исходников `Assets/Scripts/Generation/`:**
- `GalaxyGenerator.cs` — главный entry point, оркестрация этапов.
- `GalaxyGenerator.SectorStars.cs` — создание секторов, звёзд, их атрибутов.
- `GalaxyGenerator.Planets.cs` — генерация планет, орбит, имён.
- `GalaxyGenerator.Satellites.cs` — спутники.
- `GalaxyGenerator.Placement.cs` — пространственное размещение секторов + Voronoi.
- `GalaxyGenerator.Owners.cs` — разрешение Owner/Race каскадом.
- `GalaxyGenerator.Expansion.cs` — историческая колонизационная экспансия рас.
- `GalaxyGenerator.StarPhysics.cs` — звёздная и планетарная физика.
- `GalaxyGenerationContext.cs` — конфиги, пулы имён, доступные типы.
- `GalaxyUtils.cs` — `OwnerResolver`, `CustomPropertyResolver`, утилиты.
- `Galaxy/Models/*.cs` — `GalaxyData`, `StarData`, `PlanetData`, `SatelliteData`, `ShipData`.

## 2. Конвейер генерации

`GalaxyGenerator.Generate(seed, galaxyKey)` выполняет 12 этапов, каждый — измеряется секундомером и логируется:

```
1. PreReserveFixedNames          — резерв имён из премейд-конфига
2. ComputeSpacingParams          — расчёт MinStarDistance и SectorRadius
3. GenerateSectors               — создание секторов (premade + добор jitter-grid)
4. GenerateStars                 — добор звёзд до cfg.StarsCount
5. ResolveAllOwners              — каскад Owner/Race (sector → star → planet)
6. TryPlaceSectorPositions       — размещение секторов по PlaceHint
7. BuildVoronoi                  — диаграмма Воронова → области и соседи
8. BalanceStarDensityAcrossSectors — перераспределение звёзд по площади
9. ReassignStarPositions         — сэмплинг внутри полигона
10. RedistributeTooCloseSystems  — устранение нарушений MinStarDistance
11. RunExpansion (если включён)  — историческая колонизация
12. PostResolutionFinalize       — имена, начальные данные, спавн NPC
```

Если `TryPlaceSectorPositions` не сработала (слишком тесно), весь конвейер перезапускается до `MaxPlacementAttempts = 12` с подкрученным сидом.

## 3. Секторы и пространственное размещение

**Секторы** — это политико-территориальные единицы галактики. Premade-сектора из `PremadeConfig.Galaxies[X].Sectors` создаются с зафиксированными именами, владельцами и `PlaceHint`. Остальные добавляются jitter-grid’ом из `JitteredSectorPositions` (псевдослучайно по сетке с дрожанием 30% от ячейки).

### PlaceHints

`TryPlaceSectorPositions` для каждого сектора пытается до 300 раз подобрать координаты:

- `"border"` — у границы карты;
- `"center"` — внутри радиуса `min(W,H) * 0.22` от центра;
- `"corner"` — в углу;
- `"neighbour"` — около указанного `NeighbourSectorUid`.

Между секторами поддерживается минимальное расстояние `(stars_a + stars_b) * 1.2`, что эмулирует «толщину» сектора по числу звёзд.

### Voronoi

После размещения центров секторов `BuildVoronoi` строит для каждого сектора многоугольную область. Соседи определяются через ближайшую звезду к серединам рёбер. Это даёт:

- естественные политические границы;
- список соседних секторов для AI/торговли/экспансии;
- площадь для перебалансировки плотности звёзд.

### Перебалансировка плотности

`BalanceStarDensityAcrossSectors` рассчитывает целевое число звёзд на сектор пропорционально его Voronoi-площади и до 8 проходов перекидывает звёзды из «густых» в «редкие» сектора (premade-звёзды неприкосновенны). Это гарантирует, что плотность звёзд по карте отражает площадь сектора, а не первичную случайную раскладку.

### Финальное размещение звёзд

`ReassignStarPositions` для каждого сектора:
- сжимает Voronoi-полигон на `MinStarDistance / 2` (`ShrinkPolygon`);
- сэмплит позиции звёзд внутри сжатого полигона, отвергая близкие к уже размещённым.

`RedistributeTooCloseSystems` ловит оставшиеся нарушения `MinStarDistance` и пограничные случаи — переносит конфликтные звёзды в сектора с большим free-ratio площади.

## 4. Звёзды и звёздная физика

`StarData` содержит: `Type` (B/A/F/G/K/M…), `Color`, `MassSolar`, `StarRadius`, `HabitableZoneMin/Mid/Max`, `RadiationMult`, `FlareRisk`, `SystemSize`.

`FinalizeStarProps` берёт параметры типа из `Config.Stars.Types[type]` и масштабирует орбиты планет на `HZ_SizeMult` — горячие звёзды растягивают свои системы, холодные — сжимают.

Для каждой планеты дальше вычисляется `RollStellarPhysics`:

- `SolarFlux = (M^1.267 * RadiationMult) / (d/2800)²` — поток излучения.
- `BaseTemp = 278 * L^0.25 / sqrt(d/2800)` — равновесная температура.
- `MagneticField` — три формулы для разных диапазонов плотности планеты (Density < 2 / 2–3 / >3); зависит от гравитации, геоактивности и числа спутников.
- `AtmPressure` — также по формуле, зависящей от плотности.
- `SurfaceRadiation = SolarFlux * 1000 * 1.361 / ((1 + 0.36*P) * (1 + 0.36*B))` — поверхностная радиация ослабляется атмосферой и магнитным полем.
- `WaterAbundance` — зависит от геоактивности, спутников и магнитного поля; для лёгких планет = 0.
- `Greenhouse` корректирует `SurfaceTemp` по давлению и обилию воды.
- `OxygenPercent` — производится водой × магнитным полем × давлением, ослабляется потоком и геоактивностью.
- `HydrologyState` — лёд / жидкость / сверхкритика по температуре.

Это удивительно глубокая модель — учитываются физические зависимости (плотность ↔ магнитное поле ↔ давление ↔ радиация ↔ кислород), причём для каждого этапа есть fallback на «зафиксированное» значение из премейда (`AtmPressureFixed`, `OxygenPercentFixed` и т.д.).

`RollSurfaceTypes` распределяет поверхность по жидкость / горы / равнины с учётом гидрологии и геоактивности, нормализуя сумму к 100%.

## 5. Планеты и орбиты

### Создание

`CreatePlanetsRandom` для случайных звёзд: 1..MaxPlanets планет, орбитальные слоты раздаются случайно из пула.
`CreatePlanetsMixed` для premade-звёзд: сначала загружаются `FixedPlanets`, потом дополняются случайными до `targetTotal`. Premade-планеты могут указать `OrbitIndex` явно.

`CalculateNoneCount` рандомизирует число пустых (без расы) орбит — `0 … NONE_ORBIT_MAX_FRACTION` от общего числа.

### Орбиты

После создания планеты получают орбитальные радиусы и параметры:
- `OrbitEccentricity` — случайный из `[EccentricityMin..EccentricityMax]` (эллиптические орбиты).
- `OrbitTiltDeg` — случайный наклон.
- `OrbitSpeed` — случайный в обе стороны.
- `DaySpeed`, `CloudsSpeed`, `AxialTilt` — для визуала вращения.

`OrbitMath.GetEllipticPosition` потом используется и в визуале, и в AI, и в физике астероидов — единая точка правды.

### Расовая принадлежность

`EnsureRacialPlanet` гарантирует, что в системе звезды с зафиксированной расой будет хотя бы одна планета этой расы (если есть свободный слот). Это поддерживает осмысленность «звезда расы X».

### Финализация

`FinalizePlanetVisuals` назначает Graphic/Mask/Atmosphere пути из конфига по `Size` и расе. Также с шансом `ORBITAL_OBJ_CHANCE` добавляются станции/спутники.

## 6. Спутники

Аналогичный паттерн: `GenerateSatellites(parent, fixed)` сначала строит fixed-спутники, потом добивает до `SatellitesCount` случайными. `CreateSatellite` идёт через `ApplyFixedSatelliteProps`/`ApplyRandomSatelliteProps` → `FinalizeSatelliteProps`. Owner/Race наследуются от планеты.

## 7. Разрешение владельцев и рас (Owners/Races)

`OwnerResolver` — это формальная система каскадного разрешения:

1. Если у parent (сектор/звезда) **зафиксирован** Owner — он распространяется на детей.
2. Если у parent нет зафиксированного — Owner агрегируется из детей:
   - один уникальный Owner → он становится parent;
   - несколько → `OWNER_MIXED_KEY`;
   - нет → `OWNER_NONE_KEY`.
3. То же для Race.

`ResolveAllOwners` дважды вызывается в конвейере — первый раз для предварительной картины, второй раз после `RunExpansion` (если экспансия включена).

`PostResolutionFinalize` после всего этого ещё раз обходит звёзды:
- разрешает имена планет (`ResolvePlanetName`) — с учётом пула имён по расе;
- если у звезды нет имени, берёт его из имён планет (`ResolveStarNameFromPlanets`);
- инициализирует данные планет (`ItemFactory.InitPlanetData`);
- вычисляет `NameRenderData` (как отображать смешанное владение);
- спавнит NPC через `NpcSystemSpawner.PopulateStarWithNpcs`.

## 8. Экспансия рас (RunExpansion)

Опциональный этап (`Config.Settings.Expansion == 1`), моделирующий историю колонизации **от даты начала колонизации каждой расы до даты старта игры**:

1. Сначала **очищаются** все non-premade-планеты (Race/Owner → None) — экспансия начинается с чистого листа.
2. Для каждой расы читается `ColonizationStartDate` и `ColonizationSpeed` из конфига. Если дата раньше InitialDate — раса получает бюджет `(years_passed * speed)` шагов колонизации.
3. Расы обрабатываются по возрастанию даты — кто раньше начал, тот сначала колонизирует.
4. **Фронтир** — список звёзд, где раса уже присутствует (изначально — premade-звёзды этой расы).
5. На каждом шаге выбирается ближайшая некoлонизированная звезда в радиусе от `12` до `40` ед. с приоритетом:
   - тот же сектор + сразу обитаема (`sameFull`);
   - тот же сектор + терраформируемая (`sameTf`);
   - другой сектор + обитаема (`otherFull`);
   - другой сектор + терраформируемая (`otherTf`).
6. Найденная звезда колонизируется (`ExpansionColonizeStar`): все её планеты, отвечающие условиям расы (habitable или terraformable), помечаются её расой; терраформируемые — терраформируются (`ExpansionApplyOptimal`).
7. Создаётся `ExpansionEdge` — линия колонизации с годом, используется на карте.

Результат — реалистичные «лепестки» расовой экспансии, видные в `GalaxyMapGraphics`.

## 9. Имена и пулы

`GalaxyGenerationContext` хранит пулы имён по расам (`StarNamesByRace`, `PlanetNamesByRace`) + общий пул (`CommonStarNames`, `CommonPlanetNames`). При генерации имени:

1. Сначала пробуется пул нужной расы (планета с расой X получает имя из пула X).
2. Если пул пуст или взято всё — общий пул.
3. Если и он пуст — fallback `UNNAMED_S_n`.

Использованные имена живут в `UsedStarNames`/`UsedPlanetNames` для предотвращения дублей внутри одной галактики.

## 10. Условия обитаемости и терраформинга

`CheckRaceConditions` (для расовых планет) проверяет, выживет ли раса на данной планете:

- **Habitable check** — серия min/max диапазонов из `RaceConfig.PlanetConditions`: WaterAbundance, OxygenPartial, AtmPressure, SurfaceRadiation, Gravity, SurfaceTemp.
- Если **не обитаема**, проверяется **Terraformable check** (более широкие диапазоны Tf*). Если успех — раса терраформирует, ставит `IsTerraformed = true`.
- Если и не терраформируется — раса покидает планету (Race/Owner → None).

Это создаёт самосогласованную галактику, где раса не «висит» на планете, на которой не выжила бы.

## 11. Оценка системы

### Сильные стороны

1. **Детерминизм по сиду.** `UnityEngine.Random.InitState((int)(actualSeed ^ ...))` в начале каждой попытки даёт **полностью воспроизводимый** мир. Это бесценно для багов, поделиться картой, replay-ов и тестов.
2. **Чистая декомпозиция через partial class.** Один логический класс, разнесённый по 9 файлам по этапам жизненного цикла, — очень удачный приём. Каждый файл фокусируется на одной фазе, легко найти.
3. **Удивительно глубокая физика.** Формулы магнитного поля, давления, кислорода, гидрологии — не «слепленные», а взаимосвязанные. Возможность зафиксировать любое значение премейдом (`*Fixed`) даёт авторскую гибкость поверх процедурной модели.
4. **Хороший конвейер с логированием.** Каждая фаза измеряется секундомером и пишет время в лог — это сразу даёт картину горячих мест и помогает оптимизировать.
5. **Воссоздание истории через RunExpansion.** Раса колонизирует от своей starting-даты со своей скоростью, оставляя видимые `ExpansionEdge`. Это превращает галактику из «случайного шума» в осмысленный пейзаж.
6. **Premade + procedural миксуются.** Конфиг может зафиксировать сектор/звезду/планету целиком, частично или оставить полностью случайной — гибрид, дающий и контроль, и разнообразие.
7. **Voronoi для границ.** Естественно решает проблему политических областей. Площади используются для балансировки плотности — двойное использование одного расчёта.
8. **Каскадное разрешение Owner/Race** в `OwnerResolver` через единые правила, плюс агрегация снизу-вверх — единообразное правило для трёх уровней иерархии.
9. **Самосогласованность.** `CheckRaceConditions` не позволяет расе «жить» на нежизнеспособной планете — генерация не оставляет дыр в логике мира.
10. **Имена с пулами по расе.** Расовые имена + общий пул + fallback на UNNAMED — три уровня деградации, нигде не падает.

### Слабые стороны и риски

1. **Сложность конвейера.** 12 этапов с двойным `ResolveAllOwners`, два разных списка «всех звёзд» (`StarsMap` + sector.Stars), потенциальная рассинхронизация при переносах. Один баг в `RedistributeTooCloseSystems`/`BalanceStarDensity` может оставить звезду в двух секторах или ни в одном.
2. **`MaxPlacementAttempts = 12`.** Если конфиг плохо настроен (слишком много секторов на слишком маленькую карту), генерация просто бросит исключение через 12 попыток. Лучше явно подсказывать в логе, что увеличить — `GalaxyGridSize`, `MinStarDistanceParsecs` или `SectorCount`.
3. **`StarPlaceMaxIter = 10000`.** Жёсткий fallback на центроид при невозможности разместить — может дать визуально странную раскладку. Стоит хотя бы логировать процент таких fallback’ов.
4. **Магические числа во всех файлах.** `BorderZoneFrac = 0.22`, `CornerZoneFrac = 0.18`, `NeighbourRadiusFrac = 0.20`, `ExpansionRadiusStart = 12`, `StellarD0 = 2800` — слишком много констант, которые балансёр захочет править без перекомпиляции.
5. **`RollStellarPhysics` — статический метод с длинными формулами.** Без юнит-тестов риск регрессии при правке высок. Формулы заслуживают отдельного `PlanetPhysicsCalculator` с тестами на эталонные случаи (Земля, Венера, Марс).
6. **`RunExpansion` стирает существующее владение.** Если premade-конфиг настроил сектор «Empire владеет 10 звёздами», RunExpansion затрёт всё и перестроит заново. Это документировано неявно — может быть сюрпризом для дизайнера.
7. **O(N²) в Expansion и RedistributeTooCloseSystems.** Поиск целей колонизации обходит все звёзды × все фронтиры. На галактике из 1000+ звёзд это может быть медленно. Пространственный индекс (grid/quadtree) дал бы существенный выигрыш.
8. **Имена не персистируются между запусками.** `UsedStarNames` сбрасывается на `Reset()`. Если планируется DLC/расширение галактики — потребуется отдельный механизм.
9. **`CalculateSatelliteCount` и подобные** живут в `GenerationHelpers` — было бы полезно иметь явный модуль `ProceduralSizing` с понятной API.
10. **Логика `EnsureRacialPlanet`** срабатывает только если есть планета с расой `None` — если все планеты звезды уже имеют чужую расу, рассовая планета не появится. Зависит от случайной раздачи рас на premade-звёздах.
11. **`AvailableStarTypes` распределяется равномерно** — `Random.Range(0, count)`. Тип звезды (тяжёлая голубая vs красный карлик) распределяется по равной вероятности, хотя в реальности 76% звёзд — это M-карлики. Стоит ввести weight в `Stars.Types`.
12. **`GenerationHelpers.GetRandomPlanetGraphic`** работает по строковому `size` — нет проверки на отсутствие графики, при опечатке в конфиге планета окажется без визуала.
13. **`PostResolutionFinalize` смешивает разные обязанности** — разрешение имён, инициализация ItemFactory и спавн NPC. Стоит разделить.
14. **Спавн NPC внутри генерации.** `NpcSystemSpawner.PopulateStarWithNpcs` вызывается из `PostResolutionFinalize` — генерация мира знает о NPC. Лучше держать как отдельный этап, который можно отключить.
15. **`OrbitTiltDeg` рандомизируется в `[0..360]`,** но используется как наклон плоскости орбиты — это вращение всей системы. Если речь о наклоне относительно эклиптики, диапазон неестественный.
16. **Нет верификации результата.** После генерации никто не проверяет инварианты (нет звёзд без сектора? все планеты привязаны к звезде? все Owner валидны?) — это бы хорошо ловило баги в конвейере.

### Качество кода

- **Очень хорошее структурно.** Partial class разрезан осмысленно, методы лаконичны.
- **Стилистика однородна** между файлами.
- **Логирование** на ключевых фазах — отлично.
- **Документация** минимальная — стоит написать архитектурную диаграмму конвейера (наподобие этого документа) и поместить рядом с кодом.
- **Тесты отсутствуют.** Для системы такой сложности это серьёзный пробел: формулы физики, OwnerResolver, ParseNoneCount — все они чистые и легко тестируемы.

**Итог: 8/10.** Одна из самых сильных систем проекта. Глубокая физика, продуманная экспансия рас, детерминированный сид и гибкий конвейер делают её ядерной ценностью. Ключевые задачи на доработку — вынос балансных констант, добавление юнит-тестов на формулы и `OwnerResolver`, пространственный индекс для O(N²) горячих точек, верификация инвариантов после генерации.
