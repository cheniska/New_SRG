# Система ИИ (NpcAI) — описание и оценка

## 1. Общая архитектура

Система ИИ построена по **трёхуровневой иерархии**, где каждый уровень отвечает за свой масштаб принятия решений:

```
NpcSystem (точка входа, тикает все звёзды)
   └─ NpcController (MonoBehaviour, прокси к данным + анимация спрайта)
        └─ NpcBrain  (стратегия: оценка ситуации, выбор активности)
             ├─ Directive (директива фракции/расы — высший приоритет)
             └─ NpcAction (тактика: что делать — Atack/Flee/Trade/Mine/…)
                  └─ NpcOrder (приказ: как выполнить — MoveTo/Attack/Dock/…)
```

**Ключевые файлы:**
- `Assets/Scripts/NpcAI/NpcSystem.cs` — статический тикер, обходит все звёзды.
- `Assets/Scripts/NpcAI/NpcController.cs` — MonoBehaviour-обёртка, обновляет визуал по итогам хода.
- `Assets/Scripts/NpcAI/NpcBrain.cs` — мозг: классы поведения, оценка целей, переключение активностей.
- `Assets/Scripts/NpcAI/NpcAction.cs` — 15 тактических действий.
- `Assets/Scripts/NpcAI/NpcOrder.cs` — 17 атомарных приказов.
- `Assets/Scripts/NpcAI/NpcDecisionTable.cs` — таблица решений по уровню отношений.
- `Assets/Scripts/NpcAI/FactionDirective.cs` — 7 типов директив (Attack/Defend/Escort/…).
- `Assets/Scripts/NpcAI/NpcSpawner.cs` — спавн NPC у планет.
- `Assets/Scripts/Ships/ShipPersonality.cs` — модель личности (6 параметров).
- `Assets/Scripts/Core/DirectiveManager.cs` — singleton, хранит и тикает директивы.

## 2. Уровень 1 — Brain (стратегия)

`NpcBrain.Tick()` каждый ход выполняет следующее:

1. **TickPersonality** — затухание персональных модификаторов отношений (вендетты).
2. **TickStrengthCache** — пересчёт «силы корабля» раз в 10 ходов (или 3 хода, если рядом угроза).
3. **EvaluateDirective** — проверка директив от `DirectiveManager`: если есть применимая, она выполняется и блокирует обычную логику.
4. **EvaluateSituation** — если директивы нет, проверяется HP (если ниже `Personality.FleeHullPercent` — бегство или ремонт), затем включается логика боевого класса.
5. **TickActivity** — выполнение текущего `NpcAction`.

### Боевые классы (CombatClass)

Класс определяется типом корабля (`NpcBrain.ResolveCombatClass`):

| ShipTypeId | Класс       | Базовая активность         | Доминирующая логика                                     |
|------------|-------------|----------------------------|---------------------------------------------------------|
| Dominator  | Military    | `ActionDefend(центр)`      | Атака врагов по приоритету, преследование преступников  |
| Pirate     | Pirate      | `ActionPatrol`             | Грабёж торговцев, атака слабых, бегство от сильных      |
| Transport  | Civilian    | `ActionTrade`              | Бегство; запрос перемирия у пиратов (если осторожен)    |
| Ranger / * | Mercenary   | `Trade`/`Scavenge`/`Patrol`| Атака при шансе на победу, защита союзников при Tribalism |

### Личность (ShipPersonality)

Шесть параметров [0..100], генерируются из `PersonalityRange.ForShipType()`:

- **Aggression** — порог `EngageThreshold` (агрессивные дерутся при меньшем шансе на победу).
- **Caution** — порог `FleeHullPercent` (осторожные бегут раньше).
- **Greed** — мотивация к торговле, грабежу, принятию выкупа за перемирие.
- **Discipline** — обязательность выполнения директив (`Directive.ShouldObey`).
- **Tribalism** — лояльность союзникам, приоритет защиты.
- **Vendetta** — глубина запоминания обид (кап персональных модификаторов).

Личность модифицирует **отношение к конкретной цели** через `PersonalRelationModifiers` — словарь UID → штраф/бонус. После атаки враг получает штраф; после принятия перемирия — бонус. Каждый ход модификаторы стремятся к нулю со скоростью `(100 - Vendetta) / 100`.

### Оценка целей

`NpcBrain.EvaluateTarget()`:

1. Получить базовое отношение `OwnerRaceRelationsManager.GetRelation(...)`.
2. Прибавить персональный модификатор личности.
3. Применить `DecisionTable.Evaluate(relation, targetClass)`:
   - `0–19`: Attack;
   - `20–39`: Attack кроме Civilian;
   - `40–49`: Attack только Military/Pirate;
   - `50–74`: Ignore;
   - `75+ и Civilian`: Protect;
   - `100`: Protect всегда.
4. Применить личностные override’ы:
   - При очень высокой Aggression — атака даже мирных целей;
   - При высокой Greed во время атаки + наличии астероидов — `LootInstead`;
   - При Tribalism>70 — игнор не-союзников;
   - Шанс на победу `ChanceToWin < EngageThreshold` → отступление или игнор.

### Сила корабля

`NpcBrain.CalculateStrength()` суммирует:
```
firepower (сумма средних уронов оружия) + currentHull*0.3 + armor*0.5 + shield*0.2
```
Используется в `ChanceToWin = self / (self + enemy)` для прогноза боя.

## 3. Уровень 2 — Actions (тактика)

`NpcAction` — абстрактный класс с методом `Tick(ship, star, ctx) -> bool` (true = завершено). Каждое действие содержит один или несколько `NpcOrder` в качестве «строительных блоков».

**Боевые:**
- `ActionPatrol` — между двумя случайными точками в системе.
- `ActionPursueAndAttack(targetUid)` — преследование и атака.
- `ActionDisable(targetUid, hullPct)` — атака до достижения порога HP цели.
- `ActionFlee(threatUid)` — бегство от угрозы.
- `ActionDefend(zone, radius)` — охрана зоны, переключение в Pursue при появлении врага.
- `ActionEscort(targetUid)` — сопровождение, переключение в Pursue при угрозе подопечному.

**Экономические:**
- `ActionTrade` — последовательный облёт планет.
- `ActionDeliver(A, B)` — фазовая логистика (MoveA → LoadWait → MoveB → UnloadWait).
- `ActionRob` — фазы Disable → Negotiate → Loot; повышает `CrimeRating` на 15.
- `ActionMine(zone)` — поиск астероида + 3 цикла добычи.
- `ActionScavenge` — случайные пролёты по сектору в надежде найти добычу.

**Вспомогательные:**
- `ActionRetreatAndRepair` — путь до дружественной планеты + 5 ходов простоя → восстановление HP.
- `ActionRecon` — обход всех планет звезды.
- `ActionHyperJumpTo(starUid)` — выход к краю системы + смена `CurrentStarUid`.
- `ActionRequestCeasefire(aggressorUid)` — переговоры с агрессором.
- `ActionIdle(turns)` — простой.

## 4. Уровень 3 — Orders (механика приказов)

`NpcOrder` — абстрактный класс, инкапсулирующий **одно** конкретное намерение: поставить таргет, поджать дистанцию, перепрыгнуть звезду и т.п. Каждый приказ имеет `Execute()` (один раз за ход) и `IsCompleted()`.

| Приказ                | Назначение                                                  |
|-----------------------|-------------------------------------------------------------|
| OrderMoveTo           | Прибытие в точку (порог 0.5 ед.)                            |
| OrderFollow           | Лететь за кораблём с дистанцией 1.5                         |
| OrderOrbit            | Круговое движение вокруг точки                              |
| OrderDock             | Подлёт к планете + ожидание                                 |
| OrderUndock           | Отход на 1.5 ед. в случайном направлении                    |
| OrderHyperJump        | Гипер-переход в другую звёздную систему                     |
| OrderAttack           | Сократить дистанцию до радиуса оружия, удерживать           |
| OrderHold             | Удержание точки N ходов                                     |
| OrderFlee             | Лететь от угрозы на 10 ед.; кламп по радиусу системы (0.85) |
| OrderLoot             | Подлёт к точке с лутом                                      |
| OrderTransfer         | Передача предмета другому кораблю                           |
| OrderScan             | Сканирование цели на расстоянии 2.0                         |
| OrderRequestCeasefire | Переговоры о перемирии (отдать % груза)                     |
| OrderIdle/OrderWait   | Простой N ходов / по условию                                |
| OrderPatrol           | A↔B-маршрут                                                 |

Все приказы используют общую утилиту `SetMoveTarget()`, которая через `ShipTrajectory.BuildPath()` строит обход звезды по физическим waypoints.

## 5. Директивы фракций (FactionDirective)

`DirectiveManager` (singleton) — высший слой управления, выдающий приказы кораблям через `Owner` или `Race`. Применяется только если `Directive.ShouldObey(ship, ctw)` истинно (зависит от `Personality.Discipline`):

- `> 70` Discipline → выполняет всегда;
- `< 40` → игнорирует;
- иначе — выполняет, если оценка шансов на победу ≥ `EngageThreshold`.

**Реализованные директивы:**
- `DirectiveAttackSystem(ownerId, starUid)` — все корабли владельца идут в систему и атакуют врагов.
- `DirectiveDefendSystem(ownerId, starUid)` — гарнизон в зоне.
- `DirectiveRetreat(fromStar, toStar)` — массовый отход.
- `DirectivePatrolTraderoutes` — патруль.
- `DirectiveSuppressPiracy(starUid, crimeThreshold=20)` — охота на высоко-криминальных NPC.
- `DirectiveEscortConvoy(convoyUids, destStar)` — сопровождение конвоя.
- `DirectiveLockdownTrade(starUid)` — торговая блокада.

Директивы могут истекать по времени (`TurnsRemaining`) или по событию (например, конвой добрался — `IsExpired = true`).

## 6. Спавн и интеграция

`NpcSystemSpawner.PopulateStarWithNpcs` запускается во время финализации генерации (`PostResolutionFinalize`). Логика:

1. Берётся случайный фракционный Owner у планет звезды.
2. Race выбирается каскадом: звезда → сектор → первая обитаемая планета владельца.
3. Спавнится `Mathf.Clamp(planets/3, 1, 4)` NPC у планет владельца со скаттером `SystemSize*0.0005`.
4. Через `ItemFactory.EquipStarterKit` навешивается базовое снаряжение.
5. NPC регистрируются в `star.Ships`, а `NpcController.Init` лениво создаёт `NpcBrain`.

Тикинг происходит в `NpcSystem.TickAllSystems` — обходит все звёзды, у каждого живого не-игрового корабля вызывает `Brain.Tick`.

## 7. Оценка системы

### Сильные стороны

1. **Чистое разделение слоёв.** Стратегия / тактика / механика — три ясно очерченных уровня, каждый легко тестировать и расширять. Добавление нового поведения сводится к написанию одного класса.
2. **Полная отделённость от Unity.** Brain / Action / Order — обычные C#-классы, не зависят от `MonoBehaviour`. Это идеально подходит для пошаговой симуляции: NPC можно тикать в любых системах, в том числе вне рендеринга.
3. **Богатая модель личности.** Шесть осей × персональные модификаторы дают эмерджентное разнообразие поведения без раздувания кода. Особенно удачен механизм Vendetta как «памяти» о конфликтах с естественным затуханием.
4. **Многоуровневое разрешение целей.** Каскад «отношения → таблица решений → личностные override → ChanceToWin» даёт продуманную и читаемую логику атаки/бегства.
5. **Кеш силы.** `_strengthCacheAge` с разной частотой (10 ходов в мире / 3 хода в бою) — здравая оптимизация для часто вызываемого `ChanceToWin`.
6. **Директивы.** Хорошо абстрагированный слой «стратегического AI» — фракции могут вести разные кампании, не меняя кода кораблей. Истечение по событию или по таймеру упрощает оркестрацию.
7. **Кэш AliveShip ссылок.** Большинство `Order` хранят прямую ссылку на цель после первого поиска и обходят полный список лишь при необходимости.

### Слабые стороны и риски

1. **Строковые ключи активностей.** `EvaluateSituation` возвращает строку `"Flee:UID"`, парсинг разбит в `SetActivity` через `StartsWith`. Это шумно, легко ошибиться при добавлении новой активности и плохо рефакторится — лучше enum + struct/Result.
2. **Дублирование поиска кораблей.** `FindShip`, `FindNearestEnemy`, `FindVictimUid`, `FindWeakEnemyUid`, `FindOverwhelmingThreatUid` — почти одинаковые циклы. Можно вынести в единый `EnumerateShips(predicate)` с предикатами.
3. **O(N²) в `ActionEscort.FindThreatTo` и `ActionDefend.FindEnemy`.** Для каждой пары кораблей делается проверка отношений. На системе с 30+ кораблями это уже заметно при ежегодном тике 365 раз.
4. **Жёсткие константы в коде.** `MaxEngageRange = 10`, `ChaseRadius = 8`, `FollowDistance = 1.5`, `CrimeRating += 15` — все эти числа лучше унести в `GameSettingsConfig` или JSON, чтобы балансёр мог править без перекомпиляции.
5. **Зашитая логика классов.** `MilitaryLogic`, `PirateLogic`, `CivilianLogic`, `MercenaryLogic` — это код, и добавление нового класса требует правки `NpcBrain`. Желательно превратить в данные (state machine из конфига) или хотя бы в strategy pattern с регистрацией.
6. **`OrderFlee` пересчитывает направление каждый ход, но цель — фиксированная точка.** Корабль может «вилять» при движении угрозы. Стоит сглаживать направление или пересчитывать только при значимом смещении угрозы.
7. **`ActionRetreatAndRepair` восстанавливает HP мгновенно одним пакетом** после 5 ходов простоя — нарушает ощущение прогресса. Лучше регенерировать порционно.
8. **Грабёж в `ActionRob` пропускает фазу `Loot`** — добыча происходит сразу в фазе `Negotiate`, после согласия. `Phase.Loot` объявлена в enum, но не используется. Возможно, недозавершённая фича — стоит либо реализовать, либо убрать.
9. **`PerformRobbery` берёт 50% веса каждого стака,** что для одного объекта (вес 5) даёт 2.5 → округление 3. Это часто превышает то, что есть, и зависит от веса, а не количества предметов — нелогично.
10. **`ChanceToWin` оценивает себя по кэшу, цель — каждый раз заново.** Если в системе 20 кораблей и каждый оценивает 20 целей за ход, `CalculateStrength` зовётся 400 раз. Большая возможность кешировать силу по всем кораблям одним проходом.
11. **`DirectiveManager` не имеет приоритизации.** Если у `Owner` две директивы, берётся первая подходящая. Для конфликтующих директив (Attack одной системы + Defend другой) победитель определяется порядком выдачи. Лучше явный приоритет.
12. **`Directive.ShouldObey` использует фиксированный `chanceToWin = 0.5f`** из `DirectiveManager.GetDirectiveActionFor` — не учитывает реальную силу против реального противника директивы.
13. **`OrderHyperJump` мгновенно переключает `CurrentStarUid`** — переход без анимации/события. Это годится для пошаговой симуляции, но визуальный слой не получает сигнала о прыжке.
14. **`NpcSpawner` всегда выбирает одного случайного Owner’а на звезду.** Если в системе планеты двух фракций, корабли спавнятся только одной — реалистичности страдает.

### Качество кода

- **Хорошее.** Имена методов и параметров читаемы. Комментарии лаконичны, объясняют замысел, а не описывают код.
- **Стилистика однородна** между Action и Order.
- **Логирование** через `Debug.Log` присутствует на ключевых событиях (ограбление, перемирие, гиперпрыжок), но может засорить консоль на большой галактике — стоит вынести флагом.
- **Тестов нет.** Brain/Action — чистые классы, отлично подходят для юнит-тестов; их отсутствие — существенный пробел.

### Сводная оценка

| Критерий                | Оценка | Комментарий                                                          |
|-------------------------|:------:|----------------------------------------------------------------------|
| Архитектурная ясность   |   9/10 | Чёткие три уровня, лёгкое расширение                                 |
| Гибкость поведения      |   8/10 | Личность + директивы дают много вариаций                             |
| Производительность      |   6/10 | O(N²) в нескольких местах, можно кэшировать силу всех кораблей       |
| Конфигурируемость       |   5/10 | Слишком много магических чисел в коде                                |
| Сопровождаемость        |   7/10 | Дублирование поисков + строковые ключи активностей мешают            |
| Тестируемость           |   8/10 | Классы чистые, но тестов нет                                         |
| Полнота фичей           |   8/10 | ActionRob недореализован; некоторые директивы декларативны           |

**Итог: 7/10.** Зрелая, хорошо спроектированная система с понятной слоистой архитектурой. Главные направления развития — вынос балансных констант в конфиг, замена строковых ключей активностей на типобезопасные сущности, кэширование силы и устранение O(N²) в поиске целей/угроз.
